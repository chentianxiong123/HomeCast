# speaker-latency-mock —— 音箱拉流延迟黑盒测试台

独立 mock（**不属于主程序，不参与构建/测试**）：用真实小米音箱 token 下发播放命令，
监测"音箱真正开始拉流"的时刻，量化并定位"真系统点播放到音箱出声要三四秒"的根因。

## 为什么有这个 mock

真系统（`go/` 后端）里，从点播放到音箱出声有 3~4 秒延迟，一直找不到瓶颈在哪。
这个 mock 把变量拆开逐个测：命令下发时刻、音箱首次拉流时刻、拉流次数、喂流字节、
音频格式，用真实音箱做黑盒对照实验，最终定位根因。

## 跑法

```bash
cd explore/speaker-latency-mock
go build -o sptest2 .
./sptest2
# 浏览器打开 http://<本机LAN_IP>:28777  （音箱要能访问到本机，故用 LAN IP 不是 127.0.0.1）
```

依赖：
- `~/.config/homecast/speaker.json` 里的音箱 token（主程序登录后生成）
- 局域网内有在线的小米音箱
- `ffmpeg`（转码实验用）

web 页可以选设备、填 B站 BV 号，点不同按钮做对照实验：
- **播放到音箱(B站)**：音箱拉本项目 `/audio/{bvid}`，代理真 B 站 m4s
- **本地m4s / 本地mp3**：喂本地文件，对照不同格式
- **实时转码mp3推**：m4s → ffmpeg 转 mp3 → 边转边喂音箱 + 落缓存（最终方案）

## 关键结论（详见 `../../../docs/` 排查文档）

**"点播放到音箱出声三四秒"的根因 = B 站音频源是 fMP4/m4s 容器格式**，
不是命令慢、不是网络、不是音箱硬件：

| 喂流格式 | 出声前拉流 | 结论 |
|----------|-----------|------|
| fMP4/m4s | 拉满几乎整首（48 次 / 13MB） | 音箱要凑 `moov` 头 + 足量可解码片段才出声 |
| mp3 | 瞬发（3 次 / 1.9MB） | 流式帧格式，拿到第一段即解码出声 |

**解法**：喂音箱前把 m4s 软转码成 mp3（ffmpeg `libmp3lame`，纯 CPU，几十倍实时，
无需硬解），音箱拿到第一段 mp3 即出声 → 延迟从三四秒压到 ~1 秒；转码同时落 mp3 缓存，
同曲二次播放秒发。
