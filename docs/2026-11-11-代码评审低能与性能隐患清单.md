## 一、🔴 P0 性能硬伤（按影响排序）

### 1. `queue.js` 全局监听 `htmx:afterSwap` 触发整页队列重建

- 位置：`go/web/assets/queue.js:155` `document.addEventListener('htmx:afterSwap', render);`
- 现象：监听**没过滤 target**，页面里任何 htmx 片段 swap（搜索、翻页、收藏、设置）都触发 `render()`；render 是 `view.innerHTML = html` 全量重建 + 4 次 `querySelectorAll().forEach` 重绑事件（`queue.js:111,117,140,147`）。队列 100 首时点一次搜索就重建 100 张卡片 DOM。
- 修法：参照同仓 `go/web/assets/speaker.js:59` 的写法，只在 `#queue-view` 自己（或其子节点）被 swap 时才 `render()`；或者干脆去掉这行，改用 `hcBus.on('queue')` 驱动（现在 state.js 已在推 queue 事件）。
- 验收：在队列打开时做一次搜索/翻页，DevTools 看 `.queue-view` 的 DOM mutation 计数——不应随无关 swap 增长。

### 2. `state.js` 注释「节流到 ~250ms」，代码里根本没有节流

- 位置：`go/web/assets/state.js:54-56`（`applyProgress` 里 `hcBus.emit('state', ...)` 无 throttle）
- 现象：注释撒谎。每条 SSE progress（web 250ms 一条 + 音箱 1s 一条）都进 `player.js:419` 的 `hcBus.on('state', () => { driveAudio(); render(); updateMediaMeta(); })`，即每秒至少一次完整 render。
- 修法：`applyProgress` 里加 250ms 节流（`performance.now()` 判 last 或 `requestAnimationFrame` 合帧），或者让 `applyProgress` 直接写 Alpine store 不 emit 'state'（只有字段真正变化的 state 事件才 emit）。
- 验收：播放中打开 DevTools，`player.js` 的 `render` 调用频率应从 ~4Hz 降到「只有真实状态变化时」。

### 3. `player.js render()` 每帧无条件重写 SVG innerHTML

- 位置：`go/web/assets/player.js:41` `el.toggle.innerHTML = ...`；`player.js:91` `el.mode.innerHTML = MODE_ICONS[mode]`；`player.js:238` `updateMediaMeta` 每次 `new MediaMetadata` + 重复 `setActionHandler` 4 次。
- 现象：同文件标题/封面已做 `!==` 才写（`player.js:49-51`），这两处 SVG 却没做，被 #2 放大后每秒数次销毁重建。
- 修法：SVG 写前判 `el.mode.title !== ...` / 当前 icon hash；`updateMediaMeta` 里 metadata 只在 title/cover 变时重建，action handler 只在 mount 时设一次。
- 验收：DevTools Performance 面板播放 30s，`el.toggle`/`el.mode` 的 layout 节点应接近 0。

### 4. 同一份进度数据：双 250ms POST + 双 SSE 广播

- 位置 A：`go/web/assets/player.js:281` timeupdate 里 250ms 一次 `hcState.progress(...)` **和** `reportWidget()`（`player.js:294` 另有 POST `/api/v1/widget/state`）——同一进度两条 HTTP。
- 位置 B：`go/server/server.go` 的 `bridgeSpeakerProgress`（1s ticker 灌进 playback → `/api/v1/state/stream`）**和** `go/internal/api/speaker.go:26 Events`（另一个 1s ticker 推 `/api/v1/speaker/events`）——同源数据推两遍。
- 现象：SSOT 重构后 `/api/v1/speaker/events` 基本冗余，前端 `state.js`（收 state/stream）和 `speaker.js`（收 speaker/events）各收各的。
- 修法：删 `api/speaker.go Events` + `speaker.js` 对它的订阅，音箱进度统一走 `/api/v1/state/stream`；`reportWidget` 若仍需要就保留，否则也并进 state/command。
- 验收：`grep -rn "speaker/events" go/web/assets` 应为 0；`/api/v1/state/stream` 一个连接即可驱动音箱面板。

### 5. `proxy.go` 每次请求新建 `http.Client{}` 且无超时

- 位置：`go/internal/api/proxy.go:44` `client := &http.Client{}`
- 现象：不共享连接池（每次 new 一个），且 **Timeout=0**——上游 CDN 挂起就永久占 goroutine+连接。投屏大文件容易踩。
- 修法：包级共享 `var proxyClient = &http.Client{Timeout: 60 * time.Second}`，`req` 用 `http.NewRequestWithContext(r.Context(), ...)`，下游断连时上游也能取消。
- 验收：上游返回 5s 后断连的场景下，proxy goroutine 应在客户端断开后 1s 内退出（`goroutine` 数不涨）。

### 6. SQLite 裸跑：无 busy_timeout / WAL / MaxOpenConns

- 位置：`go/internal/store/db.go` `sql.Open("sqlite3", path)` 无参数
- 现象：cache 的 `evictLocked`/`Put` 持锁写盘 + playback `persistNow` 每次状态变更写 settings + fav 写表，多 goroutine 并发写同一文件，没 busy_timeout 就随缘 `database is locked`。
- 修法：DSN 用 `"sqlite3"` → 打开后 `db.Exec("PRAGMA journal_mode=WAL")` + `db.Exec("PRAGMA busy_timeout=5000")`；或 `db.SetMaxOpenConns(1)`（写密集小库最稳）。ncruces 驱动支持这些 PRAGMA。
- 验收：并发 50 个 `POST /api/v1/state/progress` + 触发一次缓存淘汰，无 `database is locked` 日志。

### 7. `TokenStore` 无 TTL、无上限、无清理

- 位置：`go/internal/service/token/token.go:29`
- 现象：每次投屏/音箱播放 `Store` 一个 token 永久躺 map，"token expired or invalid" 只是文案，`Get` 永远命中。长驻进程内存涨 + 老 URL 长期有效（放大 #14 的 SSRF 窗口）。
- 修法：`TokenEntry` 加 `ExpireAt int64`，`Store` 写入时 `time.Now().Add(30*time.Minute)`；`Get` 过期返回 false；加一个 5min ticker 定期 `GC` 掉过期项 + 超上限（如 1000 条）时 LRU 淘汰。
- 验收：跑 1 小时后 `TokenStore` 长度不无限增长。

## 二、🟡 P1 前后端不一致 / 协议不统一 / 正确性

### 8. speaker 控制端点吞错还返回 200

- 位置：`go/internal/api/speaker.go:180-204`（Play）、`:205-227`（Control）、`:234-264`（SetVolume）、`:268-274`（PlayerStatus）
- 现象：
  ```go
  res, err := h.Svc.Play(...)
  if err != nil { log.Printf(...) }   // 只打日志
  writeJSON(w, http.StatusOK, res)    // 照样 200
  ```
  失败也 200，前端 `player.js` 的 `speaker-play` handler 只能 `t.includes('音箱播放')` 拿 HTML 字符串猜成败（`player.js:318-326`）。其它端点走 `errResp(4xx/5xx)` + `{code,message,data}` 信封，同一套 API 两种成败语义。
- 修法：err 非空 → `errResp(w, http.StatusBadGateway, err.Error())`；前端别再做字符串匹配，改读 `res.code`。
- 验收：把小米 token 改成非法后调 `/api/v1/speaker/play`，HTTP 状态非 200 且 body.code≠0。

### 9. `quality` 前后端语义打架（音质按钮实为装饰）

- 位置：前端 `go/web/assets/player.js:156,346` 存 `64/128/192`；`go/internal/api/music.go Stream` 里 `quality==0` 才换 `bilibili.PreferredQuality=30280`，否则把 192 当 **B 站 qn 码**直接发 `playurl?qn=192`（无效 qn）；缓存 key 也只有 bvid 不含音质。
- 现象：用户切 64k/128k 实际都 fallback 到 `QualityPriority` 第一个（30280）；命中缓存时连音质参数都不看。音质切换 = 装饰。
- 修法：前后端统一 qn 码（`30216/30232/30280`），前端存 `30280` 之类；缓存 key 改成 `bvid+quality`（`cache.FilePath(bvid, quality)`），或切音质时主动清缓存。
- 验收：`?quality=30216` 拿到 64k 文件（Content-Length 明显小于 30280）；切音质后重拉新文件。

### 10. CORS 头写了三遍

- 位置：`go/server/server.go withCORS`（全局）+ `go/internal/api/music.go serveFile` + `go/internal/api/proxy.go stream` 各自重写一遍
- 修法：全交给 `withCORS`，删掉 handler 里的手写 `Access-Control-*`。
- 验收：`grep -rn "Access-Control-Allow-Origin" go/internal` 应为 0（只剩 server.go 一处）。

### 11. `playback.Toggle()` 与音箱模式语义分叉

- 位置：`go/internal/service/playback/playback.go` `Toggle()` 只改本地 `Playing`，不像 `Pause/Resume` 那样推 `spk.Control`
- 现象：前端 toggle 在音箱模式下自己分派 pause/resume 所以暂时没炸，但直接 `op:"toggle"` 打到音箱模式 = 假切换。
- 修法：`Toggle()` 内按 `spkActive()` 分派，或前端永远不用 toggle 走音箱。
- 验收：音箱模式下发 `op:toggle`，音箱端实际停/续（看 `speaker Control` 日志）。

### 12. 注释自相矛盾 / 与实现不符

- `go/web/assets/speaker.js` 头部注释说「1 秒轮询 progress/{did}」，下面自己打脸「轮询已废（单流 SSE）」
- `go/web/assets/state.js:54`「节流到 ~250ms」实际无节流（见 #2）
- 修法：改注释或改实现；文档和代码对齐。
- 验收：通读 speaker.js/state.js 头部注释，无矛盾。

## 四、⚠️ 安全（顺带提，非性能但严重，建议一并处理）

`go/server/server.go` 默认监听 `0.0.0.0:28976` + `withCORS` 放行 `Origin: *` + **全部端点零鉴权**。局域网任意设备（乃至浏览器里任意网页跨域）都能：

| 风险 | 端点 | 影响 |
|---|---|---|
| 拿走小米账号 passToken | `GET /api/v1/speaker/token/export` | 明文 JSON 出口，等同把密码给邻居 |
| 控制音箱/投屏 | `POST /api/v1/speaker/control`、`/cast/*` | 邻居也能推歌 |
| 清空缓存 | `POST /api/v1/cache/clear` | 删数据 |
| 内网跳板 | `GET /api/v1/proxy/{video,audio}/{token}` | token 16 字节随机不可枚举，但 #7 无过期放大窗口 |

**最小修法**（三选一，推荐第一个）：
1. 默认 `ListenAndServe` 绑 `127.0.0.1`；桌面壳需要局域网时显式开 `HC_BIND=0.0.0.0` 环境变量
2. 给所有 `/api/*` 加一个启动时生成的随机 bearer token（前端首次拿一次存 localStorage）
3. 至少 `withCORS` 把 `Origin: *` 改成同网段白名单（`http://192.168.*`）+ 校验 `Origin` 头

## 六、一句话总结

- **性能**集中在「前端每次进度事件全量重绘」+「音箱进度双链路推两遍」
- **前后不一**根子是 SSOT 重构没拆干净（quality 语义、speaker 200 吞错、`/speaker/events` 残留）
- **低能项**全是回头就能清（死代码、手写 itoa、临时诊断 log、gofmt）
- **安全洞**建议优先动手，`0.0.0.0 + CORS * + 零鉴权` 是最扎眼的那条
