# 架构探索与内聚化经验

> 日期：2026-10-17　范围：HomeCast 从「分层单体 + 命名内聚」到「业务域包 + 物理内聚」的整个摸索过程
> 状态：四步全部落地（commit `8e8d049` / `573102a` / `48ac691`），本文是沉淀，不是计划

---

## ① 目标与动机

HomeCast 从一开始就是「边做边长」：音箱推送、歌词、收藏、DLNA、三端壳……每个功能做完往 `service/` 大包一塞，包越来越大（18 文件 2790 行），**改一个业务要翻 4 层目录**。

- 动机 1：单人全栈开发，代码是自己写的但三个月后照样会忘——**找代码的成本必须降**。
- 动机 2：有个参考模板 `pi-loop-harness/framework/`（business/infra/glue 分形三层 + RULES.md 铁律），想验证「模板的哪部分真的有用、哪部分过钢」。
- 最终目标：**任何一个业务，打开项目 5 分钟内能定位**（逻辑在哪、入口在哪、表在哪、前端在哪），且这套结构能撑到项目长大。

## ② 资源拓扑（现在的结构地图——最大的成果）

### 顶层

```
homecast/
├── go/         业务核心：cmd/server（入口）+ web（htmx/模板/静态）+ internal（api/域包/协议/store）
├── wails3/     统一壳（三端）：main.go + 平台 build tag 文件 + widget/ 挂件多态 + 构建脚本
├── explore/    历史只读：legacy/（Python+Vue 老版）/ android/（手搓壳）
├── docs/       排查/架构记录（troubleshooting + 探索两种风格并存）
└── scripts/    E2E 冒烟
```

### go/internal 业务核心（重点）

```
go/internal/
├── api/          JSON 入口（每业务一个文件，薄胶水：调域包 → 写 JSON）
├── service/      业务域包（逻辑 + SQL + 表定义 + 测试 全在包里）
│   ├── music/       音乐（搜索/取流/播放）
│   ├── speaker/     音箱（推送/本地进度/自动连播）
│   ├── lyric/       歌词（解析/搜索/偏移存储）
│   ├── fav/         收藏
│   ├── playlist/    歌单
│   ├── cast/        DLNA 投屏
│   ├── sites/       站点嗅探
│   ├── widget/      挂件快照（后端状态，注意与 wails3/widget 显示层同名不同物）
│   └── token/       代理 token（跨域共享）
├── bilibili/    B 站协议客户端（infra，不动）
├── speaker/     小米音箱协议客户端（infra，不动）
├── dlna/        DLNA 协议（infra，不动）
├── store/       SQLite：只负责打开/按序建表/首启迁移（表定义不在这里！）
└── hx/          htmx 片段端点（每业务一个文件：取数 → 渲染模板）
```

### 域包间依赖（DAG，无环——手术后的关键性质）

```
music  ──→ lyric      （music 用 lyric.CleanSearchKeyword）
sites  ──→ cast       （sites 用 cast.Episode）
speaker ──→ token     （代理 URL 存储）
cast   ──→ token
其余域包独立；协议层 bilibili/speaker/dlna 只被域包依赖，不依赖域包
```

### 表定义归属（SQL 跟业务走，执行集中）

| 表 | 定义在哪 | 谁读写 |
|---|---|---|
| `favs` | `service/fav/fav.go` 的 `FavSchema` | fav 域 |
| `playlist` | `service/playlist/playlist.go` 的 `PlaylistSchema` | playlist 域 |
| `lyric_sels` | `service/lyric/lyric.go` 的 `LyricSchema` | lyric 域 |

`store.Migrate(db, schemas, legacy)` 只负责按序执行建表 + 历史 JSON 导入，**不感知具体表定义**——由装配层 `server/server.go` 把各域 schema 传入。依赖方向：`server → service + store`，无环。

### 域包文件头地图注释（内聚第二步）

```go
// Package speaker 音箱域：小米音箱推送/本地模拟进度/自动连播（xiaomusic 方法论，零小米云轮询）。
// 全链路：入口 internal/api/speaker.go · hx/speaker.go；前端 speaker_*.html ×4 + speaker.js；表：无
package speaker
```

每个域包都有，找不到代码先看注释。

## ④ 成功路径（内聚四步，可复现）

**先决条件**：老项目结构是「大包 + 命名内聚」时，按下面顺序走，每一步都可独立验证、可回退。

1. **表定义归业务域**（最小改动，先做）：
   - 每个业务文件里加 `XxxTable` + `XxxSchema` 常量（`CREATE TABLE` 原文搬过去）。
   - `store.Migrate(db, dir)` 签名改成 `Migrate(db, schemas []string, legacy map[string]string)`——**执行留在 store，定义归业务**。
   - 装配层（server.go）传入 schema 常量 + 历史 JSON 路径映射。
   - ⚠️ 千万别让 store import service（见坑 #1），只能装配层中转。
2. **全链路地图注释**：每个域包文件头加「职责 + 入口 + 前端 + 表」一行地图。零风险。
3. **service 按域拆包**（大手术，2 小时量级）：
   - `git mv` 文件到 `internal/service/<域>/`（保留历史），改 `package` 声明。
   - 编译收集错误清单 → 逐个修引用（脚本批量：符号→域包映射表 + import 重写）。
   - 跨包共享的辅助符号抽成独立小包（如 `token`）。
   - 测试跟着域走；**碰别的包内部状态的测试，归位到那个包**（见坑 #3）。
   - 包名与既有包重名的，引用处加别名（见坑 #2）。
4. **纪律文档化**：README 加「业务核心结构」节 + 四条纪律（新逻辑进域包 / SQL+表定义跟业务 / 域包自测 / 薄胶水入口），防止回潮。

**每次手术后验证流程**（固定动作）：`go build ./...` → `go test ./...`（12 包全绿）→ 重启服务冒烟（首页 200 / 业务端点 200 / 老库数据完好）。

## ⑤ 踩坑记录（现象 → 根因 → 解法）

### 坑 #1：import 环（表定义归业务的第一个坑）
- **现象**：想让 store import service 拿 `FavSchema` 常量，`go build` 报 import cycle；service 的测试 import store（验证持久化），store 再 import service 就成环。
- **根因**：service 测试 → store → service，双向引用。
- **解法**：**装配层传参**。store 不 import 任何业务包，`server/server.go` 把 schema 字符串数组 + legacy 映射当参数传进 `Migrate`。依赖方向固定为 `server → service` 和 `server → store`。

### 坑 #2：域包名与既有协议包重名（拆包手术的坑）
- **现象**：拆出 `service/speaker` 域包后，`hx/hx.go`、`hx/speaker.go`、`api/speaker.go`、`server/server.go` 四个文件同时 import `internal/speaker`（协议）和 `internal/service/speaker`（域），编译报 `speaker redeclared in this block`。
- **根因**：Go 里同一个文件两个 import 同包名就是重名。协议包 `internal/speaker` 先占用了 `speaker` 标识符。
- **解法**：给**域包**加别名 `spk "homecast/internal/service/speaker"`，域符号 `SpeakerService/PlayOpts/...` 全部改 `spk.X`；协议包的符号保持 `speaker.X` 不变。约定：**协议包优先占名，域包用别名**。

### 坑 #3：测试跨包访问内部状态
- **现象**：`lyric/lyric_search_test.go` 引用 `MusicService` 和 `viewCacheEntry`（music 包私有字段），拆包后编译失败。
- **根因**：`TestLyricsKeywords` 测的是 `MusicService.LyricKeywords` 方法，本质是 music 包的行为测试，当初写在歌词测试文件里是「按主题不按包」导致的。
- **解法**：测试**归位到所属域包**（搬到 `music/music_test.go`，同包可访问私有字段）。教训：**测试文件放哪个包，取决于被测符号在哪个包，不取决于主题**。

### 坑 #4：批量脚本 glob 判断写错
- **现象**：重写 18 个引用文件的 python 脚本，第一次跑 `待改文件: []`。
- **根因**：用 `pathlib.Path(d).suffix` 判断目录，目录无后缀 → 走了 else 分支空列表。
- **解法**：直接用 `pathlib.Path(d).glob('*.go')`，别自作聪明加 suffix 判断。

### 坑 #5：误匹配（虚惊一场）
- **现象**：grep `service.NewTokens` 发现 3 处「不存在于任何 service 文件的符号」。
- **根因**：`miservice.NewTokens()` 的子串包含 `service.NewTokens`，`grep -oh "service\.[A-Z]"` 匹配进去了。
- **解法**：用词边界 `\bservice\.` 重新匹配。教训：**全局搜符号时加词边界，miservice 类长包名会伪装成 service.。**

### 坑 #6：音箱 token 401（更早的探索，保留）
- **现象**：恢复 token 快路径后 `device_list` 空、接口 401。
- **根因**：`serviceToken` 有效期短，`restoreToken` 恢复后直接用旧值。
- **解法**：恢复后必须 `client.Login("micoapi")` 用 passToken 刷新 serviceToken（passToken 快路径无需密码），失败回退 QR。

### 坑 #7：音箱 `code: 101`（ubus invalid result）——不是代码问题
- **现象**：真机验证推送失败，ubus 返回 101。
- **根因**：**音箱关机**（用户确认「机器没开」），101 = 设备离线。
- **解法**：不是 bug，别修。教训：**协议层报错先怀疑设备状态，再怀疑代码**。

## ⑥ 验证成果（证据）

- **全量测试**：`go test ./...` 12 个包全绿（拆包后依旧），域包自带测试（speaker 3 个、lyric 4 个、fav/playlist/music 各 1-2 个）。
- **编译**：`go build ./...` 零错误；Linux 完整构建 19M 二进制可跑。
- **冒烟**：服务重启后首页 200、fav 列表 200、`/api/v1/speaker/progress/{did}` 返回 `{"state":"idle"}`。
- **老库无损**：拆表定义 + 拆包后，`homecast.db` 三张表 `favs/playlist/lyric_sels` 结构数据完好（幂等迁移验证）。
- **搜索质量升级**（更早）：BV1FPjy6TEiE 合集（总标题无歌名）从 0 候选 → 5 候选，第一候选带 yrc 逐字词，0.44s。
- **依赖无环**：`music→lyric`、`sites→cast`、`speaker/cast→token`，其余独立（编译期保证）。
- **三端壳**：Linux GTK 挂件在用；Windows 层就位待真机；安卓裸交叉编译是既有失败（wails 需完整工具链，与清理无关）。

## ⑦ 决策记录（为什么 A 不选 B）

| 决策 | 选了什么 | 没选什么 | 理由 |
|---|---|---|---|
| 域拆法 | 拆成 9 个物理域包 | 保留大包只加注释 | 物理聚合 > 命名聚合，找不到函数的痛点只有拆包能根治 |
| 接口层 | **不做** | pi-loop-harness 的 business/infra/glue 接口层 | 单人单实现，接口是空转；`LyricStore db==nil` 内存兜底是唯一第二实现场景 |
| 表定义 | 归业务域 | 集中 store/db.go | 改表结构要翻 store 是物理分散的根；执行仍集中（Migrate） |
| LyricKeywords | 留在 music 包 | 搬去 lyric 包 | 它是 MusicService 方法，依赖 VideoInfo/播放上下文（固定第一P），且 music→lyric 单向依赖比 lyric→music 干净 |
| token 存储 | 独立小包 | 塞 speaker 或 cast | 音箱和 DLNA 都用代理 URL，跨域共享必须独立 |
| 音箱进度 | 本地模拟（Started 时钟 + PausedAt 补偿 + time.AfterFunc 连播） | 轮询小米云 | 避免被拉黑；对齐 xiaomusic/MiAir 方法论 |
| 重名处理 | 域包别名 spk | 协议包改名 | 协议包（internal/speaker）引用点多，改名成本高；域包是新名字 |
| GitHub | SSH over 443 | mihomo 代理 | 用户明确弃代理；22 端口断走官方备用通道 |

### 模板铁律验证结论（pi-loop-harness/framework 对照）

**验证有效**：htmx 片段模板（api/hx 双入口薄胶水）、同包测试、SQLite 幂等迁移、按域分包。

**过钢打脸**：
- 「纯函数铁律」——`lyric.go fetchLyricRaw` / `speaker.go Play` 本质是编排 IO，硬拆纯函数反而割裂；
- 「一文件一函数」——文件 = 领域聚合单元，按文件拆函数粒度错；
- 「契约冻结」——单人快迭代，冻结是负担不是保障。

结论：**模板方向对（分层+内聚），力度错（粒度过钢）**。HomeCast 取的是宽松版：域包 + 薄胶水 + 纪律文档。

## ⑧ 未解之谜 / 下一步岔路

1. **api/ 和 hx/ 会缓慢膨胀**：阈值埋线在「25+ 文件 / 产生找不到函数的痛点」，到点再拆；纪律文档已写，不慌。
2. **service/widget vs wails3/widget 同名**：一个是后端快照、一个是显示层，名字混但注释已区分；若持续混淆可考虑后端改名 `widgetstate`（低优先）。
3. **音箱真机验证自动连播**：进度/连播代码已就绪（`speaker_progress_test.go` 4 用例绿），**音箱目前关机**，等开机跑真机。
4. **安卓明文 HTTP**（networkSecurityConfig）：要安卓端验证才有价值，排在真机后面。
5. **阶段 4 系统 hooks**（托盘/单实例）：加分项，不阻塞。
6. **双入口双写**：收藏业务 = api + hx 两处入口（7 处/4 目录已收敛为 域包 + 2 胶水），htmx 与 JSON 的边界是否要统一成一种，留待观察，不主动动。
