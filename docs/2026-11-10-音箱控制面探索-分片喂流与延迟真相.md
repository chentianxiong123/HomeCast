## 二、根因分析（对照参考项目）

### 根因 1：PlayURL 只走 player_play_url
- 主代码 `PlayURL` 只调 `player_play_url`，从没走 `play_by_music_url`
- MiAir 对部分硬件需要 music API；miservice-go 库无 `PlayerPlayMusicUrl` 方法（需自实现）

### 根因 2：needUsePlayMusicAPI 缺硬件
- 主代码 `needUsePlayMusicAPI` 缺 LX05A / L07A（用户两台设备）

### 根因 3：MiAir 对 music API 设备 pause 用 player_stop
- API 状态不更新 workaround

## 三、决定性反转：LX05A 实测 play_by_url（不是 music API）

| 参考项目 | NEED_USE_PLAY_MUSIC_API 是否含 LX05A/L07A |
|---------|------------------------------------------|
| xiaomusic | **不含**（对）|
| MiAir | 含（错）|

**实测铁证**（真实音箱 LX05A）：
- `player_play_url` → **code:0 成功** ✅

**结论**：**LX05A / L07A 用 `play_by_url`（非 music API）**——xiaomusic 列表对，MiAir 错。主代码 5ac88fe 的 music API 修复方向需**修正对齐 xiaomusic**（去掉 LX05A/L07A/L15A）。

## 四、音箱拉流机制

- **音箱是被动 HTTP 拉流方**：我们发 API 给云 → 云让音箱播 URL → 音箱从我们局域网 HTTP 拉流
- **我们持 URL 即控流**
- 音箱支持协议：`audio/mpeg, mp3, mp4, ogg, flac, wav, aac, m4a, wma, L16, adts, ape`
- 实测：音箱成功拉局域网流（`[stream] 连接: 192.168.31.9`，同网段）

---

## 五、音箱解码器预缓冲 ≈ 877KB（黑盒间接值）

- 音箱拉满缓冲就停（**预拉满，不是边播边拉**）
- **877KB = 54.8s × 128kbps** 推算
- **切源延迟 = 877KB / 比特率**（64k m4a ≈ 107s 不可接受）

---

## 六、方案 B：分片喂流（"流少→及时掉头"）

### 原理
分片让音箱解码器**永远远不满**（12KB << 877KB）：
- 播完当前段解码器空
- 切源时下一段喂新源**立即读**
- 音箱连续播放无卡顿

### 二分法实测结果
| 分片 | 大小 | 卡顿 | 延迟 |
|------|------|------|------|
| 无限喂满 | 877KB+ | 无 | **54.8s**（最差）|
| 5s | - | - | 5s |
| 1s | 24KB | - | ≤1s |
| **0.5s** | 12KB | **无** | ≤0.5s |
| **0.25s** | 6KB | **无** | 跟手 |
| 0.125s | 3KB | 无 | 跟手 |
| 0.0625s | 1.5KB | 无 | **仍 2-3s** |

### 关键发现：877KB 是"平滑陷阱"
- **877KB 一片 = 跟手最差**（正好填满缓冲 → 播 54.8s 才空 → 切源 54.8s）
- 0.5s 分片让解码器永远不满 → 切源 ≤0.5s 最好
- **分片不能无限小**：卡顿占比 ≈ δ/分片（δ=音箱时钟误差，LAN <10ms）；分片无限小 = 连续喂 = 缓冲满 = 切源慢

---

## 七、决定性反转：2-3s 是音箱固件固有延迟

**切分片从 1s → 0.0625s（16 倍缩小），延迟纹丝不动（2-3s）** → **延迟根源不是分片**。

**真相**：音箱内部有一条 **2-3s 播放管线**（解码/缓冲/固件调度），**无论喂多小分片都要 2-3s 才响**——**音箱固件黑盒，改不了**。

```
实际延迟 = 音箱固件固有延迟（2-3s 不可压） + 分片影响（已消除到 0）
```

**分片最优 = 0.25s**（分片部分压到最小 + 无卡顿；再小无意义，2-3s 音箱固有主导）。

---

## 八、内存切段（不落盘）

- 整首歌加载内存 `[]byte`（不落盘，避免文件爆炸）
- seek = 字节偏移改（时间→字节，CBR 精确换算）
- 切歌 = 换内存源
- mutex 原子读 + 推进防竞态
- 修竞态：curSong/curOffset mutex 原子读+推进
- 修"暂停没用"：handleStream 不查 paused → 加 `paused` 检查
- 修"新的放不了"：音箱播完断流（broken pipe）→ `streamDead` 标志 + play 重 `play_by_url` 重连
- 修"暂停延迟"：`player_pause`/`player_resume`，后改本地停喂（0.5s 内静音）

---

## 九、控制面架构结论

| 操作 | 走哪 | 说明 |
|------|------|------|
| 初始播放 | **必须走云** | 音箱无屏唯一能播局域网 URL 的方式 = 云下指令 `player_play_url` |
| 播放中（连接挂）：暂停/切歌/seek/播放 | **全本地** | 音箱喂什么听什么（本地停喂/换源/改偏移） |
| 流断重连（音箱播完断开） | **必须走云** | 重 `play_by_url` |

## 十、待验证：稳定供流 + 喂速=实时（热切换无感理论）

用户理论：**稳定供流 + 热切换（消费者无感）→ 无延迟**。

**关键前提**：热切换无感需要音箱**边播边拉**（解码器保持低水位，不堆积）：
- 稳定供流 + **喂太快** → 音箱拉满 877KB → 切换 54.8s（实测）
- 稳定供流 + **喂速=实时** → 音箱边播边拉 → 切换**应无感**（待验证）
- 分片（断续） → 每次空 → 2-3s（固件）

**若验证成立**：稳定供流+实时喂 = 热切换无感（最优解）。
**若仍 2-3s**：音箱固件固有延迟 = 物理下限，接受（分片 0.25s 版本），走"预读新源 + UI 即时反馈"优化感知。

---

## 十一、结论

1. **LX05A/L07A 用 `play_by_url`**（xiaomusic 对，MiAir 错）——主代码需修正对齐。
2. **音箱解码器预缓冲 ≈877KB**——分片让解码器常空 → 切源即时。
3. **分片最优 = 0.25s**（无卡顿 + 跟手部分最小）。
4. **2-3s = 音箱固件固有延迟**（分片压不动，物理黑盒）。
5. **控制面架构**：初始播放/流断重连走云，播放中全本地。
6. **待验证**：稳定供流 + 喂速=实时（热切换无感）——最后一步。
