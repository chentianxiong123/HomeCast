## 一、问题的由来：为什么 wails "不好用"？ <a id="一"></a>

### 1.1 传统做法：花里胡哨的拦截

大多数 wails 项目是这样做的：

```
用户请求
    ↓
WebView (wails)
    ↓
拦截 OnRequest（wails 回调）
    ↓
你的拦截器（Go 代码）
    ↓
自己解析 URL、处理参数、返回 HTML
    ↓
WebView 显示
```

这个方案有个致命问题：**每个端都要自己实现一遍拦截逻辑**。

- Linux：用 WebKitGTK，拦截 `OnNavigation`
- Windows：用 WebView2，拦截 `OnNavigationStarting`
- 安卓：用 WebView，拦截 `shouldInterceptRequest`

而且，**wails 官方文档给的例子就是拦截模式**，很多人就照着抄了。

### 1.2 我们的痛点

HomeCast 项目最初也走了这条路，结果踩了三个坑：

#### 坑 1：安卓 asset loader 物理限制（最致命）

wails 的安卓壳用的是 **WebViewAssetLoader**，它只能加载打包进 APK 的静态文件（HTML、JS、CSS）。**动态内容（比如 htmx 请求生成的 HTML）根本没地方放**。

我们试过三种办法，全部失败：

| 方案 | 为什么失败 |
|---|---|
| 拦截请求 → 后端生成 HTML → 返回 WebView | WebViewAssetLoader 不开放拦截接口 |
| fork wails 源码改 asset loader | 物理限制，fork 修不了 |
| 走外部 HTTP | 安卓禁止 cleartext HTTP，要配 networkSecurityConfig |

**结论**：安卓端必须走真实 HTTP，拦截方案根本走不通。

#### 坑 2：JS 通信瓶颈

wails 的 JS-Binding 设计是给 SPA 用的（Vue/React），对 htmx 这种**服务端渲染、片段替换**的模式完全不是原生的。

每次交互都要：
```
htmx 触发事件 → 调用 JS 桥接函数 → Go 执行 → 返回 JSON → JS 再调 htmx 更新 DOM
```

多绕一圈，维护成本翻倍。

#### 坑 3：各端实现不一致

- Linux 拦截器写完了
- Windows 拦截器要重写一遍（API 不同）
- 安卓连拦截都没法写

**每修一个 bug 要改三处代码**。

## 二、优雅方案的思路：wails 退到壳的位置 <a id="二"></a>

### 2.1 核心设计理念

**wails 只是个装 WebView 的容器**，它不应该管业务逻辑。

```
┌─────────────────────────────────────────────┐
│  wails 壳（窗口管理 + 系统 API）              │
│                                             │
│  ┌─────────────────────────────────────┐    │
│  │  WebView（纯粹的浏览器，什么都看不见）   │    │
│  │                                       │    │
│  │  加载 http://127.0.0.1:28976          │    │
│  │       ↑                               │    │
│  │       └───────────────────────────────┘    │
└─────────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────────┐
│  Go 后端（独立可跑，端口 28976）              │
│                                             │
│  htmx 路由 /hx/* → 渲染模板 → 返回 HTML     │
│  静态资源 /assets/* → 返回 JS/CSS/图片      │
│                                             │
│  同时支持：                                   │
│  - 浏览器访问（开发调试）                     │
│  - 浏览器嵌套 iframe                           │
│  - WebView 直接加载                          │
└─────────────────────────────────────────────┘
```

**关键洞察**：

> wails 的 `assetserver.GetStartURL()` 支持绝对 URL。
> 所以 WebView 可以加载 `http://127.0.0.1:28976`，而不是本地的 `file://` 或 `wails://`。

WebView 就是个浏览器，它不关心 URL 是本地还是远程。只要后端跑着，它就显示内容。

### 2.2 为什么要这样？

| 需求 | 拦截方案 | 优雅壳方案 |
|---|---|---|
| 三端统一 | ❌ 每端重写拦截器 | ✅ 统一 HTTP，WebView 行为一致 |
| 后端独立可跑 | ❌ 后端必须嵌进壳 | ✅ `go run ./cmd/server` 就能跑 |
| 安卓动态内容 | ❌ 物理限制，拦截不了 | ✅ cleartext HTTP 放行即可 |
| htmx 原生支持 | ❌ 要 JS 桥接，绕一圈 | ✅ 服务端直接渲染，零中间层 |
| 系统 API | ✅ wails 提供 | ✅ wails 提供 |

## 三、具体实现：五步落地 <a id="三"></a>

### 3.1 main.go：URL 改真实 HTTP

```go
// wails3/main.go（迁移后，真实代码）
func main() {
    ensureHome() // 数据目录（安卓 filesDir / 桌面 ~/.config）
    h := server.New()
    go listenBackend(h) // 后端起真实 HTTP（桌面 0.0.0.0 / 安卓 127.0.0.1）

    app = application.New(application.Options{
        Name:        "HomeCast",
        Description: "家庭音乐播放器（B站音乐 · 个人免费）",
    })

    // WebView 直接指向后端真实 HTTP（同源，非 wails asset 桥）
    app.Window.NewWithOptions(application.WebviewWindowOptions{
        Title:            "HomeCast 家庭投屏播放器",
        Width:            1280,
        Height:           800,
        MinWidth:         920,
        MinHeight:        620,
        BackgroundColour: application.NewRGB(17, 17, 17),
        URL:              "http://127.0.0.1:" + backendPort(),
    })

    if err := app.Run(); err != nil {
        os.Exit(1)
    }
}
```

**改动点**：把原来指向 wails asset 桥的 URL 改成真实 HTTP，后端独立起服务。

### 3.2 wails3 配置：WebviewWindowOptions.URL

wails v3 的 `WebviewWindowOptions.URL` 字段接受任意合法 URL，包括 `http://`。

**之前**（拦截方案）：
```go
URL: "wails://" + assetserver.GetStartURL()
// assetserver 返回 file:///path/to/index.html
```

**之后**（优雅壳方案）：
```go
URL: "http://127.0.0.1:" + backendPort()
// 后端自己起，端口随机或固定
```

### 3.3 安卓端：networkSecurityConfig 放行 cleartext（阶段 3 待做）

安卓默认禁止 cleartext HTTP（明文 HTTP），要配 `network_security_config.xml`，并在 AndroidManifest.xml 引用：

```xml
<?xml version="1.0" encoding="utf-8"?>
<network-security-config>
    <domain-config cleartextTrafficPermitted="true">
        <domain includeSubdomains="true">127.0.0.1</domain>
        <!-- 只放行 localhost，其他域名还是 HTTPS -->
    </domain-config>
</network-security-config>
```

AndroidManifest.xml 的 `<application>` 标签加引用：
```xml
<application
    android:networkSecurityConfig="@xml/network_security_config"
    ...>
```

**当前状态**：真实 AndroidManifest.xml（`wails3/build/android/app/src/main/AndroidManifest.xml`）已有 `INTERNET` 权限，但 `network_security_config.xml` 还没创建，`android:usesCleartextTraffic` 也没配。这是阶段 3 安卓迁移的大头，优先用模板化补丁（写个脚本生成 xml + 改 manifest）而非 fork wails。

### 3.4 CORS 配置

后端要响应跨域请求（WebView 虽然是同源加载，但桌面壳 wails:// 域与 http://127.0.0.1 之间跨域，挂件/局域网访问也需要）。真实代码在 `go/server/server.go`：

```go
// withCORS 允许任意来源（本地单用户服务；桌面壳 wails:// 域跨域访问）
func withCORS(h http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("Access-Control-Allow-Origin", "*")
		w.Header().Set("Access-Control-Allow-Methods", "GET, POST, DELETE, OPTIONS")
		w.Header().Set("Access-Control-Allow-Headers", "Content-Type, Authorization")
		if r.Method == http.MethodOptions {
			w.WriteHeader(http.StatusNoContent)
			return
		}
		h.ServeHTTP(w, r)
	})
}
```

配套的还有 `go/hx/hx.go` 的 `noPageCache` 中间件，页面/htmx 片段强制 `Cache-Control: no-store` —— 模板 go:embed 进二进制后，WebView/浏览器一旦缓存旧 GET /hx/* 响应，换成新二进制也看不到新 UI（本次音箱面板"还是旧版"的根因）。这两个中间件是迁移后 WebView 走真实 HTTP 的必备配套。

### 3.5 hcEnv 注入方式

**之前**（拦截方案）：后端中间件注入环境标志，WebView 里的 htmx 代码靠它判断"是否跑在壳里"：

```go
// 后端中间件注入环境标志
func injectHcEnv(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        ctx := context.WithValue(r.Context(), "hc", 1)
        next.ServeHTTP(w, r.WithContext(ctx))
    })
}
```

**之后**（优雅壳方案，真实代码）：wails 官方 `WebviewWindowOptions.JS` 直接注入到 WebView 全局作用域，前端 `settings.js/subtitle.js` 读 `window.hcEnv` 区分桌面壳/网页：

```go
// wails3/main.go
app.Window.NewWithOptions(application.WebviewWindowOptions{
    URL: "http://127.0.0.1:" + backendPort(),
    JS:  "window.hcEnv='desktop';", // 页面加载后 wails 官方注入
})
```

**为什么改**：原来后端注入是因为拦截方案里 WebView 看不到环境变量；现在 WebView 就是普通浏览器，wails 官方支持 JS 注入，直接用官方能力，不再自己写中间件。

## 四、为什么这个方案优雅？ <a id="四"></a>

### 4.1 对比：拦截方案 vs 优雅壳方案

| 维度 | 拦截方案 | 优雅壳方案 |
|---|---|---|
| **架构层次** | 4 层（拦截器 + 后端 + 桥接 + WebView） | 3 层（后端 + WebView + wails 壳） |
| **代码量** | 每端 500+ 行拦截逻辑 | 每端 50 行配置 |
| **后端依赖** | 后端必须嵌进壳 | 后端独立运行 |
| **开发体验** | 改后端要重新 build 壳 | 后端热重载，WebView 自动刷新 |
| **调试方式** | 只能真机/FQ | 浏览器直接访问后端 |
| **维护成本** | 每端独立维护 | 统一 HTTP |

### 4.2 架构优势：三层分离

```
┌─────────────────────┐     ┌─────────────────────┐     ┌─────────────────────┐
│  UI 层（htmx）       │     │  业务层（Go htmx）   │     │  系统层（wails 壳）  │
│                     │     │                     │     │                     │
│  - 服务端渲染        │ ←→  │  - 路由处理          │ ←→  │  - 窗口管理          │
│  - 片段替换          │     │  - 业务逻辑          │     │  - 托盘/单实例       │
│  - 零 JS 框架        │     │  - SQLite 持久化     │     │  - 剪贴板/对话框     │
└─────────────────────┘     └─────────────────────┘     └─────────────────────┘
         ↓                          ↓                          ↓
    WebView 加载                后端 HTTP                wails 启动后端
    http://127.0.0.1:28976      go run ./cmd/server       app.Run()
```

**为什么好**：

1. **UI 层可以独立迭代**：改 htmx 模板不用 rebuild 壳
2. **业务层可以独立测试**：`go test ./hx/` 零依赖 WebView
3. **系统层只管系统 API**：托盘、单实例、剪贴板都交给 wails

### 4.3 各端统一

无论 Linux、Windows、安卓，**WebView 都是同一个 URL**：

```
Linux:  http://127.0.0.1:28976  →  WebKitGTK
Windows: http://127.0.0.1:28976  →  WebView2
Android: http://127.0.0.1:28976  →  Android WebView
```

**UI 表现完全一致**（同源加载，没有 asset loader 差异）。

### 4.4 利用 wails 上游系统 API（阶段 4 待做）

wails v3 beta.25 的桌面系统 API 能力矩阵（读源码确认）：

| 能力 | API | 状态 |
|---|---|---|
| 单实例锁 | `Options.SingleInstance` | ✅ 已支持 |
| 系统托盘 | `SystemTray`（`newSystemTray` + `Run()`） | ✅ 已支持 |
| 剪贴板 | `Clipboard` | ✅ 已支持 |
| 文件对话框 | `OpenFileDialog` / `SaveFileDialog` | ✅ 已支持 |
| 全局快捷键 | `Accelerator` | ✅ 已支持 |
| **桌面通知** | 无 | ❌ 缺失 |
| **深链（scheme handler）** | 无 | ❌ 缺失 |

**待做（迁移阶段 4）**：定义 `SystemHooks` 接口在 `go/server` 层，由 wails 壳注入真实实现（托盘/单实例/剪贴板/对话框），通知部分回退到页面内 toast。

真实 API 示例（阶段 4 落地代码）：

```go
// 单实例（迁移时即可接入）
app = application.New(application.Options{
    Name: "HomeCast",
    SingleInstance: &application.SingleInstanceOptions{
        UniqueID: "com.homecast.app",
        OnSecondInstanceLaunch: func(data application.SecondInstanceData) {
            // 激活已有窗口，不重复启动
            app.Window.Show()
        },
    },
})

// 系统托盘（阶段 4）
tray := application.NewSystemTray()
tray.SetTooltip("HomeCast").SetIcon(iconBytes)
tray.OnClick(func() { app.Window.Show().Focus() })
tray.Run()
```

**为什么现在只做壳**：这些能力都是 `window.NewWithOptions()` 和 `SystemTray` 级别的配置，和业务代码完全解耦。等阶段 4 再做，不影响主架构。

## 五、踩坑记录 <a id="五"></a>

### 5.1 安卓 asset loader 物理限制（已解决）

**现象**：安卓 WebView 加载 `file:///android_asset/index.html`，但动态内容（htmx 请求）需要后端。

**错误尝试**：
- fork wails 改 asset loader → 修不了，WebSocket 和 WebSocket URL 是硬编码
- 自己实现 HTTP server 嵌入 APK → 包体积爆炸

**正确做法**：
- 后端独立运行（`go run ./cmd/server`）
- 安卓 WebView 加载 `http://127.0.0.1:28976`
- `network_security_config.xml` 放行 cleartext

### 5.2 hc=1 兼容路径（阶段 3 统一删）

**背景**：wails3 asset 桥不透传 `HX-Request` 头，导致后端无法区分"htmx 请求"和"普通请求"（渲染整页还是片段）。拦截方案下，前端补 `hc=1` 查询参数充数：

```go
// go/hx/search.go:51-52
// 安卓壳（wails3 asset 桥不透传 HX-Request 头）由前端补 hc=1 参数区分 htmx 请求
isHX := r.Header.Get("HX-Request") != "" || r.URL.Query().Get("hc") == "1"
```

**迁移后**：WebView 走真实 HTTP，htmx 会带 `HX-Request: true` 头，不再需要 `hc=1` 充数。

**处置策略**：保留兼容路径不动，等阶段 3 安卓端迁移完成（WebView 走真实 HTTP 后）统一删掉 `|| r.URL.Query().Get("hc") == "1"` 分支和前端 `shell.html` 里的 `hc=1` 拼接。过早删会让旧版安卓客户端坏。

### 5.3 桌面通知缺失（已知限制，已有兜底）

**现象**：wails v3.0.0-beta.25 的桌面端系统 API 里**没有桌面通知**（OS 级托盘/系统横幅）。

**已确认能力矩阵**（读 wails 源码得出）：

| 能力 | 状态 |
|---|---|
| 单实例锁 | ✅ 有 |
| 系统托盘 | ✅ 有 |
| 剪贴板 | ✅ 有 |
| 文件对话框 | ✅ 有 |
| 全局快捷键 | ✅ 有 |
| **桌面通知** | ❌ **无** |
| 桌面深链（scheme handler） | ❌ 无 |

**当前兜底方案**：前端页面内 toast（`go/web/assets/toast.js` + `hcBus.emit('toast', {msg})`）。用户打开应用时能看见反馈，但应用在后台时看不到。

**影响**：音乐播放完成通知、任务完成通知在应用后台时无法提醒。

**待办（迁移阶段 4）**：定义 `SystemHooks` 接口（`go/server` 注入），桌面端实现调用 wails 上游能力，通知部分留空/回退到页面 toast。等 wails 上游补通知 API 再接入。

## 六、架构对比总结 <a id="六"></a>

### 6.1 一句话总结

> **优雅不是不写代码，而是不写"不必要的代码"**。
> 
> 拦截方案写了 500 行拦截器、1000 行桥接、3000 行重复逻辑。
> 优雅壳方案只写了 50 行配置，剩下的交给 htmx + wails 上游。

### 6.2 决策树

```
你的项目是 htmx 服务端渲染？
    ├── 是 → 用优雅壳方案（wails 只做窗口）
    └── 否 → 评估是否需要 SPA 桥接
                ├── Vue/React + wails binding → 拦截方案
                └── 混合模式 → 部分拦截，部分 HTTP
```

### 6.3 适用场景

| 场景 | 推荐方案 |
|---|---|
| htmx + 服务端渲染 | ✅ 优雅壳方案 |
| Vue/React SPA + wails binding | 拦截方案（或等 wails 上游支持） |
| 混合模式 | 部分拦截，部分 HTTP |

---

## 结语 <a id="结语"></a>

这次架构调整的核心思路是：

> **承认 wails 的局限，不跟它对抗，而是用它的长项。**

- wails 擅长：窗口管理、系统 API、打包
- wails 不擅长：asset loader 改造、JS 桥接

我们只让它做自己擅长的（壳 + 系统 API），把业务逻辑交给 htmx 和 Go 后端。

**代价**：要跑一个后端进程。  
**收益**：架构清晰、三端统一、可独立开发测试、代码量减少 70%。

这笔账，怎么算都值。
