## 一、影响性能

### 1. 🔴 `ShortTitle` 每次调用 `regexp.MustCompile`（模板热路径）

**位置**：`go/web/web.go:51-53`

```go
func ShortTitle(t string) string {
	re := regexp.MustCompile(`《([^》]+)》|（([^）]+)）|【([^】]+)】|「([^」]+)」|\[([^\]]+)\]`)  // ← 每次调用都编译
	...
}
```

这是模板函数，`results.html`/`fav_list.html`/`results_mp.html` 里**每行数据调用 3-4 次**（`{{shortTitle .Title}}` 在 data-ctx-title / data-title / h3 里重复出现）。搜索结果 20 条 → 每次搜索 **60-80 次正则编译**。正则编译是最贵的操作之一，纯浪费。

**修法**：提为包级 `var shortTitleRe = regexp.MustCompile(...)`，函数内只 `shortTitleRe.FindAllStringSubmatch`。

### 2. 🟡 静态资源全量 `no-store`（无指纹/无 ETag）

**位置**：`hx/hx.go:101-105`（`assetHandler`）

```go
w.Header().Set("Cache-Control", "no-store, no-cache, must-revalidate")
```

所有 `assets/`（htmx.js / alpine.min.js / player.js / style.css / 图片）每次页面加载都**重新下载**。浏览器/WebView 打开页面的每个 JS/CSS 都全量重拉——`style.css` + 十几个 JS 文件，无任何协商缓存。注释说"静态资源已有 assetHandler 单独处理"，但实际是**最粗暴的 no-store**，前后不一（本意要"asset 治理为服务端最新"，代价是永远不缓存）。

**修法**：给静态资源做内容指纹（文件名带 hash）→ `Cache-Control: immutable, max-age=31536000`；或至少保留 `ETag`/`Last-Modified` 让浏览器 304 协商。页面 HTML 保持 no-store 是对的，资源不该。

## 二、低能

### 1. 🔴 SQLite 打开未配置并发（写冲突隐患）

**位置**：`store/db.go:21`

```go
db, err := sql.Open("sqlite3", path)  // 无 SetMaxOpenConns / 无 WAL / 无 busy_timeout
```

`database/sql` 默认连接池无限。多个 goroutine 同时写 SQLite（播放持久化 `persistNow`、缓存 `last_used`、收藏保存、歌词选择、`cache.go` LRU），ncruces 驱动会因并发写返回 `SQLITE_BUSY`。当前能跑是因为**偶发**，不是配置正确。SQLite 标准配置（单写者）没做。

**修法**：`db.SetMaxOpenConns(1)`（SQLite 单写者，最稳）；或至少 `db.SetMaxOpenConns(4)` + 开启 `PRAGMA journal_mode=WAL` + `PRAGMA busy_timeout=5000`。

### 2. 🔴 `LyricStore` 有内存缓存却不用（DB 模式下每次查库）

**位置**：`lyric.go:416-424`

```go
func (s *LyricStore) Get(bvid string) (LyricSel, bool) {
	...
	if s.db == nil {
		v, ok := s.mem[bvid]   // ← 只有无库时才用 mem
		return v, ok
	}
	err := s.db.QueryRow(...).Scan(...)  // ← db 模式每次查 SQLite
```

`SetSelection`/`SetOffset` 都写 `s.mem[bvid]`，但 `Get` 在 db 模式下**跳过 mem 直接查库**。`mem` 形同虚设，每次取歌词源都打 SQLite（`SelectedSID`/`Get` 高频调用）。**前后不一**：写有缓存、读没缓存。

**修法**：`Get` 先查 mem（命中即返），mem miss 再查 db 并回填 mem。

### 3. 🟡 sites 详情页集数缓存无过期

**位置**：`sites.go` `CacheEpisodes`/`GetCachedEpisodes`

`episodesCache` 有 `cached_at` 字段，但 `GetCachedEpisodes` **从不检查它**——缓存永久有效，页面内容更新了仍返回旧集数。存了 `cached_at` 不用（死字段 + 无 TTL 两合一）。

**修法**：`GetCachedEpisodes` 检查 `cached_at`，超过 TTL（如 24h）视为 miss；或删 `cached_at` 字段明确"永久"。

### 4. 🟡 fav `Add`/`Remove` 全表重写

**位置**：`fav.go` `Add` L60-71 / `Remove` L73-81 / `save` L39-56

每次加/删收藏：`load()` 全表读 + `save()` 事务内 `DELETE FROM favs` 再逐条 INSERT 全部。收藏 500 条 → 每次操作写 500 行。为保持"新增在前"顺序用全表重写，过于粗暴。

**修法**：`Add` 用单条 `INSERT`（rowid 最大即最前）或 `ON CONFLICT`；`Remove` 单条 `DELETE`。避免全表重写。

### 5. 🟡 sites `save()` 无锁（lost update）

**位置**：`sites.go` `Add`/`Remove` 调 `load()`（持锁）后 `save()`（**不加锁**）

`load()` 加 `s.mu`，`save()` 不加。`Add`/`Remove` 两个操作之间（load 释放锁 → save）其他 goroutine 可改 → 后写覆盖先写（丢更新）。**锁前后不一**。

**修法**：`Add`/`Remove` 全程持锁，或 `save` 也加锁。

### 6. 🟢 死字段若干

- `fav.FavSong.PlayCount`（`fav.go`）：声明了、迁移了，Go 侧**从不更新**（无播放计数 API）。
- `sites.episodesCache` 结构体：定义但**从未实例化**（实际用 `map[string]any`），且内含 `_ interface{}` 占位字段。
- `sites.episodesCache.CachedAt`：存了从不读（见 #3）。

**修法**：删死字段/死结构体，或补上真正使用。

## 三、前后不一

### 1. 🟢 `CleanSearchKeyword` 按字节截断中文（乱码风险）

**位置**：`lyric.go:79`

```go
if len(s) > 40 {
	s = s[:40]   // ← 按字节截断，可能切在 UTF-8 多字节中间
}
```

`[40]` 是字节，若第 40 字节落在中文中间 → 非法 UTF-8 → 网易云搜索关键词乱码 → 歌词匹配失败。B站标题含中文几乎必中。

**修法**：`[]rune(s)[:40]`（按字符截断），或 `utf8.RuneCountInString` 判断。

### 2. 🟢 `migrateJSON` 逐条 INSERT 无事务

**位置**：`store/db.go:79-84`

首启迁移几百条 JSON **逐条 `db.Exec`**（每条自动提交一次）。一次性但慢，且中途失败留半套数据。

**修法**：包一个 `tx`，批量 INSERT 后 commit。
