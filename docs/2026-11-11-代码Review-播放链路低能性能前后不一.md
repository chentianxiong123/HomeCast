## 一、前后不一（真 bug 级，最该先修）

### 1. 🔴 `Next()` 投送失败回滚，`Prev()` 投送失败不回滚

**位置**：`go/internal/service/playback/playback.go` L296-303（Next） vs L333-341（Prev）

- `Next()`：`spk.Play` 失败 → 回滚 `QIdx` + `applyLocked(oldSong)`，状态回旧歌。
- `Prev()`：`spk.Play` 失败 → **只打日志，状态已切到新歌**，但音箱还停在旧歌。前端显示"切过去了"，实际音箱没动 → 界面与物理状态分裂。

**修法**：把 `Next()` 的回滚逻辑抽成公共函数，`Prev()` 失败时同样回滚。

**附带问题（回滚不完整）**：回滚后 `applyLocked(oldSong)` 把 `Position=0` 清零（L348-356），但音箱实际还在播旧歌的 30s 处，UI 会闪到 0，等下个 progress 桥（1s tick）才推回来。回滚应恢复 `oldPosition`/`oldDuration`，而非 `applyLocked` 一刀切。

### 2. 🔴 音箱自动连播后，`BVID` 与 `QIdx` 脱钩

**位置**：`playback.go:SetSpeakerProgress` L486-505

音箱本地定时器 `playNextAuto`（`speaker.go:playNextAuto`）切到下一首后，progress 桥把 `p.cur.BVID = 新歌`，但 **`p.cur.QIdx` 仍指旧歌**。后果：
- 队列高亮错位（高亮旧歌，实际在播新歌）；
- 用户再点"下一首"，`Next()` 从 `queue[QIdx+1]` 走位，可能既非当前歌也非正确下一首。

SSOT 内部自相矛盾。

**修法**：`SetSpeakerProgress` 里当 `bvid != p.cur.BVID` 时，按 `bvid` 在 queue 中找 `QIdx`（找不到则不动或追加）。

### 3. 🔴 `Toggle()` 是漏网之鱼——同类方法里唯一不碰音箱

**位置**：`playback.go:Toggle` L234-240

`Pause()`/`Resume()` 都走 `spk.Control(did, "pause"/"resume", 0)`，唯独 `Toggle()` 只翻转本地 `Playing`，不调音箱 API。前端 `player.js:126` 现走 `pause`/`resume` 未踩，但 `Toggle()` 暴露在 `state.go` 的 `op="toggle"` 入口，谁调谁在音箱模式失效。

**修法**：要么补上音箱分支，要么删掉 `op="toggle"`，别留半吊子。

### 4. 🟡 音质 `30280` 硬编码 ×4，且自动连播丢音质

**位置**：
- `playback.go:293`（Next）、`playback.go:335`（Prev）
- `server.go:speakerControllerAdapter.Play`
- `speaker.go:resumeProgress`（`playNextAuto(did, p.NextBVID, 30280)`）

`SpeakerProgress` 不存原 quality。用户 128k 播放 → 暂停 → 恢复 → 自动连播下一首时被**静默换成 192k**。

**修法**：`SpeakerService.Play` 把 quality 存入 `SpeakerProgress`；`resumeProgress`/`playNextAuto` 用存的值，删魔法数。

### 5. 🟢 `bcastSnapshot` vs `bcastProgress` 双通道，`Pause/Resume/Toggle/Seek/SetProgress` 只走 progress

**位置**：`playback.go` L142-160

`Pause()`/`Resume()`（L202-231）只发 progress——播放态 true→false 是"状态"变化，不是"进度"变化，却只走轻量通道，前端 `state.js:applyProgress` 要承担状态语义。建议 pause/resume 也 `bcastSnapshot`。

## 二、影响性能（实打实的浪费）

### 1. 🟡 web 播放时每 250ms 打 2 个独立 POST（8 req/s）

**位置**：`player.js:278-281`

```js
window.hcState.progress(...)  // → POST /api/v1/state/progress
reportWidget();               // → POST /api/v1/widget/state
```

同一份进度数据，两条 HTTP 链路，各 4Hz。且后端 `widget.Set()` → `BroadcastLyricState()` 每条日志打一行（见 #2）。

**修法**：`reportWidget` 的 payload 完全包含在 `progress` 里；后端 `state/progress` 顺手调 `widget.Set()`，前端只发一个请求。

### 2. 🟡 `BroadcastLyricState` 每 250ms 一条 `log.Printf`（4 条/秒）

**位置**：`widget.go:229`

```go
log.Printf("[widget] BroadcastLyricState bvid=%s ct=%.1f line=%q offset=%.1f", ...)
```

播放 1 小时 = 1.4 万条日志，还带完整歌词行字符串。

**修法**：删掉或降为 debug，只在 bvid 变化时打。

### 3. 🟢 前端用 120ms `setInterval` 轮询，而非 Alpine 响应式订阅

**位置**：`player.js:388-401`

```js
setInterval(() => { const p = pb(); const key = ...; if (key !== last) {...} }, 120);
```

每 120ms 无条件读一次 `Alpine.store('playback')`。Alpine 3 有 `Alpine.effect` / `alpine:store` 事件可订阅，这里用轮询+key 对比。

**修法**：挂 `Alpine.effect` 或监听 `alpine:store`。

### 4. 🟢 `render()` 单帧内调 `pb()` 4 次

**位置**：`player.js:63,73,75,77`

顶部已 `const p = pb()`，L73/75/77 还在反复调 `pb()` 读 store。

**修法**：用顶部 `p`，删掉重复调用。

### 5. 🟢 `bridgeSpeakerProgress` 无条件 1s tick

**位置**：`server.go:bridgeSpeakerProgress`

即使无音箱在播，每秒 `svc.AllProgress()` 也加 `speaker.mu` 锁 + 遍历 map + 为每个 did 调 `pb.SetSpeakerProgress`（又加 `pb.mu`）。

**修法**：`AllProgress()` 为空时提前返回；或在 `SpeakerService` 加 `HasActive()`。

## 三、低能（设计/实现上的"将就"）

### 1. 🔴 `SpeakerAuth.Hardware` 是共享可变字段，跨设备并发会串

**位置**：`speaker.go:267,380,386,394` + `speaker/auth.go:56`

```go
s.Auth.Hardware = device.Hardware   // Play() 在 s.mu 之外直接赋值
ret, err = s.Auth.PlayURL(device.DeviceID, proxyURL)  // 内部按 Hardware 分文
```

两台不同硬件（如 L07A + 普通）设备并发操作（一台切歌、一台调音量），`Hardware` 互相覆盖 → `NeedPlayMusicAPI` 分文反转 → 该走 `play_by_url` 的走了 `play_by_music_url`，音箱无声。

**修法**：把 `hardware` 作为 `PlayURL` 参数传入，不塞共享结构体。

### 2. 🟢 `Progress()` 和 `AllProgress()` 是两份几乎一样的 map 组装

**位置**：`speaker.go:Progress` L281-299 vs `AllProgress` L301-321

两处 `map[string]any{"state","bvid","title","position","duration","next_bvid"}` 构造完全重复。

**修法**：抽 `progressMap(p *SpeakerProgress) map[string]any`。

### 3. 🟢 三套 JSON 响应写法并存

**位置**：`speaker.go`

`errResp(w, ...)` / `writeJSON(w, 200, {...})` / `ok(w, ...)` 混用；且 `Play/Control/SetVolume` 返回 `map[string]any{"code":404,...}` + 可能带 `err`，前端要自己看 `code`；其他 API（`state.go`）用 `{code,message,data}` 信封。两套约定并存，`speaker.js` 要区分处理。

### 4. 🟡 `Next()`/`Prev()` 里 `isSpk` 和 `spkActive()` 双份判断

**位置**：`playback.go:287,289` 与 `:329,331`

锁内算 `isSpk = Source=="speaker" && did!=""`，解锁后又调 `spkActive()` 重算。且 `spkActive()` 内部又加锁（有的调用方持锁调、有的解锁调）——锁模式前后不一，易改出死锁。

**修法**：只留 `spkActive()`，删 `isSpk` 局部变量。

### 5. 🟢 `SetSpeakerProgress` 里条件不对称

**位置**：`playback.go:489-497`

```go
if title != "" { p.cur.Title = title }       // 判空
if duration > 0 { p.cur.Duration = duration } // 判 >0
p.cur.Position = position                     // 无条件覆盖
```

`position` 无条件覆盖——若某次上报偶发 `position=0`（暂停回 0 瞬间），会把正在播的歌进度砸回 0。建议 `position` 也做来源校验（带 `playing` 语义）。
