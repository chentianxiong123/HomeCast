# 多平台歌词控制统一方向（减少适配难度）

> 背景：HomeCast 是「前后端一律真实 HTTP，wails3 只当系统壳」的架构。
> 现在要往**多平台**（web / 桌面 GTK 挂件 / 安卓悬浮窗 / 未来 Windows 挂件、iPad 小窗…）扩。
> 多平台最大的难题 = **同一套歌词控制逻辑，散在几个平台各写一份 → 适配难度爆炸**。
> 本文是一个**方向把握 + 试探实验**：怎么统一、怎么把"每加一个平台"的适配成本降下来。
> 不是最终定死的设计，是**先试通、验证了再固化**。

---

## 0. 一句话方向

> **逻辑一份住后端，平台只做"渲染 + 系统接口适配"；平台间靠一条真实 HTTP + SSE 通道通信。**
> 每加一个平台 = 加一个"渲染壳"（画出来）+ 若干"系统接口"（权限/穿透/点击），
> **不碰核心逻辑**——这是"减少适配难度"的根。

---

## 1. 多平台的根本难题（为什么散就完了）

以歌词控制为例，真正要统一的**只有一件事**：

> **"当前播放位置 + 当前歌词数据 → 该显示哪一行"（位置→行 定位）**

这件事**天然只有一份**（歌词解析、行定位算法、offset 对齐）。
但它出现在几个"显示终点"上：

| 显示终点 | 进程 | 语言 | 系统接口 |
|---------|------|------|---------|
| web 字幕条 | 同进程（WebView 内） | JS | DOM |
| 桌面 GTK 挂件 | 独立窗口 | Go + cgo | X11 穿透/置顶 |
| 安卓悬浮窗 | 独立 Service | Java | `SYSTEM_ALERT_WINDOW` 授权 |
| （未来）Windows 挂件 | 独立窗口 | Go + Win32 | 透明/点击 |
| （未来）iPad 小窗 / 车机 | ? | ? | ? |

**难题**：如果"位置→行"这份逻辑**在每个显示终点各写一遍**（JS 一份、Go 一份、Java 一份），
那么——

- 改一次定位规则（比如加 offset、加 KTV 进度）→ **改 N 遍、N 种语言**，必漏；
- 每个新平台**重复实现**核心逻辑 → 适配成本线性涨；
- 各平台显示**不一致**（同一时刻算出不同行）。

**这就是"多平台歌词控制"的根难题**：核心逻辑与显示终点**耦合**了。

---

## 2. 减少适配难度的方向（核心思想）

### 原则：**逻辑 / 渲染 / 系统接口 三层解耦**

```
┌──────────────────────────────────────────┐
│ ① 核心逻辑层（一份，住后端 Go）            │
│    · 位置快照（前端上报，缓存在后端）       │
│    · 歌词数据（后端本地 /music/lyric）      │
│    · 位置→行 定位算法（唯一一份）          │
│    · 产出：当前该行文本 + 该行宽           │
└───────────────┬──────────────────────────┘
                │ 一条真实 HTTP 通道（SSE 推送，不轮询）
                │  event: lyric-state
                │  data: {bvid, ct, playing, line, max_width}
┌───────────────▼──────────────────────────┐
│ ② 渲染层（每个平台各自"画"，纯哑终端）      │
│    · web：DOM  setText                    │
│    · 桌面：GTK  paint                     │
│    · 安卓：TextView setText              │
│    → 收 line 就画，自己不写定位逻辑        │
└───────────────┬──────────────────────────┘
                │
┌───────────────▼──────────────────────────┐
│ ③ 系统接口层（每个平台各自"接"）           │
│    · 安卓：授权 canDrawOverlays / 点击     │
│    · 桌面：X11 穿透 / 置顶 / Alt+Tab 隐藏  │
│    · 新平台：它自己的系统 API             │
│    → 只接系统，不碰逻辑                    │
└──────────────────────────────────────────┘
```

**为什么这样能减少适配难度：**

- **加新平台 = 只写 ② 渲染 + ③ 系统接口**（几十行，画 + 接系统），
  **不碰 ① 逻辑**（一份，后端）→ 适配成本**不再随平台数线性涨**（核心逻辑 0 成本）。
- **核心逻辑改动只改一处**（后端），全平台自动一致。
- **显示终点可以是任意形态**（浮窗/字幕条/小窗/车机），只要会"收 SSE 画一行"。

### 关键判断：**"位置→行"住后端 还是 住前端？**

这是方向把握的**唯一岔路**，两种都"统一"，但成本结构不同：

| 维度 | 前端算（逻辑住 JS） | 后端算（逻辑住 Go）✅ |
|------|-------------------|----------------------|
| 逻辑真正一份 | 否：JS 一份 + 各显示层还得转 | **是**：Go 一份，显示层纯渲染 |
| 平台显示一致性 | 需把算好的行推给各显示层（绕路） | SSE 直达，天然一致 |
| 前端不活着（暂停/锁屏/没开 webview） | 没人算，挂件死 | **后端快照还在，还能算** |
| 链路 | 前端 POST→后端→SSE→显示层（4 跳） | 前端只报位置快照，SSE 带 line（1 跳） |
| 加新平台 | 每个新显示层都要会收 line | 每个新显示层只需 setText(line) |

**试探结论**：**"位置→行"住后端**是减少多平台适配难度的方向。
理由：显示终点**天然是多进程/多语言**（GTK/Java/DOM），逻辑若住前端（JS），
要么绕 4 跳推给每个显示层，要么每个显示层各写一份（=散掉）。**住后端，一条 SSE 广播所有显示层，
加平台只加渲染壳。**

> 注：web 字幕条在**前端进程内**，它就近自己算（同套算法，不绕 HTTP）是合理特例——
> 因为 web 显示层和"播放位置源"同进程。独立显示层（桌面/安卓）才需要走 SSE 收后端算好的行。

## 3. 试探实验（先试通再固化）

**实验目标**：验证「核心逻辑一份住后端 + 显示层纯渲染」这条路在**现有代码上**走得通，
成本可接受，**不为了一致性引入过度抽象**。

### 实验 1：后端"位置→行"产出，SSE 带 `line`
- 后端 `WidgetState` 拿到位置快照 + 本地歌词行 + offset，算出当前行文本。
- SSE `lyric-state` 多带一个 `line`（+ 可选 `max_width`，本歌窗口宽，切歌定死播放中不变）。
- **验收**：订阅 `/widget/events`，`POST /widget/state` 后能看到带 `line` 的推送。

### 实验 2：显示层退化成哑终端
- **桌面挂件**：`applyState` 直接用 SSE 的 `line`，**删本地 `displayIdxLocked`/行定位**。
- **安卓悬浮窗**：`applyState` 直接 `setText(line)`，**删 Java `pickLine`/`cachedLines`/拉 `/music/lyric`**。
- **验收**：删掉本地定位后，桌面/安卓**仍正确显示当前行**（逻辑来源变后端）。

### 实验 3：加"假平台"验证扩展成本
- 临时写一个**最小显示层**（比如一个独立小 Go 程序 / 或一段 curl 模拟），
  只订阅 SSE + `print(line)`，模拟"未来某个新平台"。
- **验收**：这个"新平台"**没碰后端一行代码**，只写"订阅+打印"就显示了 → 证明加平台成本低。
- 实验完**删掉**（是试探，不是产品）。

### 实验 4：一致性
- 同一首歌、同一 `current_time`，**web 字幕条 / 桌面 / 安卓**显示**同一行**。
- 改一次定位规则（比如 offset），**只改后端**，三端同时变 → 证明逻辑真一份。

### 实验 5（可选）：特殊接口隔离
- 安卓"点击切播放/暂停"、桌面"穿透/置顶"——确认这些**只动 ③ 系统接口层**，
  不污染 ① 逻辑层（加它们不影响后端算行）。

## 4. 风险 / 边界（先想清楚再固化）

| 风险 | 判断 |
|------|------|
| **后端要能"算"** 依赖：位置快照（前端报）+ 歌词行（后端本地）+ offset | 都有现成数据，**不新增数据源**；位置快照前端**本来就报**（`/widget/state`），只是以前报了让前端自己算，现在改了后端顺手算掉。 |
| **切歌才拉歌词行**（低频） | 行数据不每帧拉；bvid 变拉一次缓存，逐帧只读缓存定位。与现在桌面挂件 `fetchLyric` 缓存一致。 |
| **KTV 进度** | 行 `[sec,text,dur]`，dur 缺失用"下一行 sec − 当前 sec"兜底（对齐 web lyric.js，算法一份，住后端）。 |
| **offset 只首载应用** | `t = ct + offset`，offset 来自 `Lyric.Get(bvid).Offset`（与 web 一致）。 |
| **web 字幕条例外** | 它在前端进程就近算（同套算法）——**不是写两份**，是"同进程就近"的合理优化；算法本身仍对齐后端那份。 |
| **过度抽象风险** | 不为"未来 iPad/车机"现在就抽接口/框架——**先把 1/2/3 试通**，抽象等真有两个以上独立显示层落地时再提。试探≠大重构。 |

---

## 5. 结论（方向把握）

- **方向**：核心逻辑（位置→行）**一份住后端**；平台显示层**纯渲染 + 系统接口适配**；
  平台间靠**真实 HTTP + SSE 推送**（不轮询）通信。
- **减少适配难度**：加平台只加"渲染壳 + 系统接口"，**核心逻辑 0 成本**；改规则只改一处，全端一致。
- **先试探实验**（本文 §3 五个实验）验证这条路在现有代码上成本可接受，**试通了再固化成正式设计**。
- **不做**：不现在抽大框架/接口；不为了"未来平台"预写代码；web 字幕条保持就近（特例）。

> 一句话：**逻辑一份住后端，平台只做壳；一条 SSE 串所有壳。先试通，再固化。**

---

## 附：落地顺序（试探实验 → 固化）

1. 实验 1（后端算行 + SSE 带 line）→ 通 = 方向成立。
2. 实验 2（桌面/安卓退化成哑终端）→ 通 = 适配难度确实降了。
3. 实验 3（加假平台验证扩展成本）→ 通 = 扩展模型成立。
4. 实验 4（一致性 + 改一处全变）。
5. 实验 5（特殊接口隔离确认）。
6. 全通 → 固化为正式设计文档 + 提交推送；不通 → 回退，重新把握方向。
