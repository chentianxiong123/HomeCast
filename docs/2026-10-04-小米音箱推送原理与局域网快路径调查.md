# 小米音箱推送原理与"局域网快路径"调查记录

日期：2026-10-04

## 背景

HomeCast 要看的功能稳不稳，我打算验证小米音箱登录/推送这块。用户问了我两个问题：**推文件还是推流？局域网还是一定联网？** 又提出一个猜测：**HA 的米家集成有两条路径（云端 + 局域网快路径），我们能不能用？**

## 一、推送原理（代码级）

扒了自己 `go/internal/speaker/` + `service/speaker.go` + miservice-go 底层，结论：

**推流（URL 式），不是推文件。控制走云端，音频流走局域网。**

```
控制面（播放/暂停/音量）：HomeCast → 小米云 miio RPC（RemoteUbusCall）→ 音箱     ← 必须联网
音频面：B站CDN →(联网,referer防盗链)→ HomeCast 本地代理 →(局域网)→ 音箱自己拉流解码 ← 音箱要能访问 localIP
```

miservice-go 底层实锤（`miservice/mina.go:202`）：

```go
RemoteUbusCall(deviceId, "mediaplayer.player_play_url",
    H{"url": <代理URL>, "type": 2, "media": "app_ios"})
```

HomeCast 只给音箱下发一个 **URL 地址**（`http://<localIP>:28976/api/v1/proxy/audio/<token>`），音箱自己拉流解码。代理 URL 由 HomeCast 带 referer 从 B站 CDN 拉 DASH 音频转发（防盗链靠 HomeCast 解）。

**两个"网"都要**：
| 链路 | 网络要求 |
|---|---|
| 控制（HomeCast→小米云→音箱） | 必须联网 |
| 音频（音箱→HomeCast 代理） | 必须局域网（人不在家就用不了） |
| 取流（HomeCast→B站） | 必须联网 |

## 二、HA 双路径调查（用户问的对不对？）

用户记得 HA 米家集成有两条路径——**对的，但那是普通米家设备**：

| 路径 | 适用 | 协议 |
|---|---|---|
| 云端（Cloud） | 所有设备 | 小米云 miio RPC |
| 局域网（Local） | 支持 miot-spec in LAN 的设备 | **miIO UDP 直连**（54321/22470 端口，设备 token 加密握手）|

局域网路径的关键——**设备 token 我们能拿到**：miservice 的 `HomeDeviceList`（`/home/device_list`）返回里就有 `DeviceInfo.Token`。Go 生态里 miservice **没有**局域网 UDP 实现（它只有云端），要自己写（协议不复杂：AES 加密 JSON，python-miio 有参考）。

## 三、扒 HA 源码：音箱是例外

从 GitHub 拉了 `al-one/hass-xiaomi-miot` 的 `custom_components/xiaomi_miot/media_player.py`（1057 行），把音箱实体（XiaoAiCloudPlayerEntity）的播放路径全查了：

| 动作 | 实现 | 通道 |
|---|---|---|
| URL 播放 | `player_play_url` → `api2.mina.mi.com/remote/ubus` | 云端 |
| 音乐播放 | `async_play_music`（micoapi music payload 包 stream.url）| 云端 |
| 语音/非 URL | `intelligent_speaker` 动作 `execute_text_directive` / `play_text` | 云端 |
| 状态轮询 | `player_get_play_status` → ubus | 云端 |
| 普通 miot 实体 | `play_media()` 直接 `return False` | 不支持 URL 播放 |

**media_player.py 里根本没有 local/miio 分支**。原因：音箱的媒体服务（小爱播放引擎）只在云端开放，固件不开放局域网播放端口。HA 都躺平走 cloud，侧面说明局域网直连对音箱不现实。

## 四、意外发现（对验证有用的差异）

HA 的 `player_play_url` 传的 **type 是媒体类型字符串**（`audio/mpeg`/`video`），**而 miservice-go 硬编码 `type: 2`**（数字类型码）。如果某些音箱型号不认数字 type，可能**静默播放失败**。

**这是小米播放链路验证的第一个观察点**：播不动就改成传 MIME 类型（对齐 HA 用法）再试。

另外我们代码里 `needUsePlayMusicAPI` 有一张硬件表（X08C/X08E/X8F/X4B/LX05/OH2/OH2P/X6A，"部分硬件需要用 play_music_api"），但 service.Play **统一走 PlayerPlayUrl，没有对表内硬件分支**——这些型号可能是 URL 播放兼容性的雷区。

## 五、结论

1. 局域网快路径对**音箱没有**——维持现状（控制走云端 + 音频流本地代理）是主流唯一成熟做法
2. 小米验证重点回到现有链路：登录三式（账密/token 恢复/二维码）→ 播放兼容性（type 参数、硬件表）→ 状态轮询
3. 登录链路不需要真音箱就能先验（二维码生成 → 扫码 → token 落盘 → 重启恢复 → 设备列表）；播放链路要真音箱同网
