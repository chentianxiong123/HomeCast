# 歌词控制统一架构（全端一致 · SSE 推送 · 后端算行）

> 沉淀时间：2026-11-06
> 背景：桌面 GTK 挂件、安卓悬浮窗、web 字幕条 三端歌词"各写一份本地算行逻辑"，
> 用户理念要求**逻辑一份、前端 UI 适配、特殊接口适配**，且**废轮询要推送（SSE）**。
> 本文是改代码前的构思/思想/决策记录，代码改动见后续 commit。

---

## 一、要解决的核心问题

### 现状（坏）
三端歌词**各写了一份"当前行定位"逻辑**（三份算法一样、三种语言）：

| 端 | 算行逻辑 | 位置 |
|----|---------|------|
| 桌面挂件（Go） | `displayIdxLocked()`：`sec <= pos` 找最后一行 | `wails3/widget/widget.go` |
| 安卓悬浮窗（Java） | `pickLine(ct)`：`sec <= ct` 找最后一行 | `wails3/build/android/.../LyricOverlayService.java` |
| web 字幕条（JS） | 行循环 `lines[i][0] <= t` 找 idx | `go/web/assets/subtitle.js` |

**问题**：逻辑"反复适配"——改了行定位规则（比如加 offset、加 KTV 进度）要改三处、三种语言，必漏。
**用户要求**：**逻辑必须一份**，前端 UI 做适配、特殊接口做适配。

### 附加问题
- 安卓悬浮窗**没有控制面板、没有点击交互**（纯 TextView），桌面有（⏸/±/🔒/✕）→ UI 欠。
- 桌面挂件曾靠 **900ms 轮询** `/widget/state`，安卓 **500ms 轮询** → 用户"废轮询要推送"。

## 二、两条候选方案对比（关键决策）

"播放位置（`audio.currentTime`）→ 当前歌词行" 这段**唯一逻辑**放哪里？

### 方案 A：前端算行
```
前端 subtitle.js 算好当前行 → POST /widget/state { ..., line } → 后端 SSE 转发 → 显示层 setText(line)
```
- 优点：播放位置天然在前端（`audio.currentTime`），算行最准。
- **巨大问题**：
  1. 桌面挂件 / 安卓悬浮窗是**独立进程/显示层**，不在 WebView 里，前端算完**够不着**，得绕 4 跳
     （前端 POST → 后端 → SSE → 显示层）。
  2. **高频**：前端 250ms 一次 POST（带 line），纯为传一个字符串。
  3. **前端不活着（暂停 / 没开 webview / 锁屏）没人算**，挂件空白/卡死。

### 方案 B：后端算行 ✅（选定）
```
前端只上报"位置快照"（POST /widget/state {bvid, current_time, playing, ...}，低频校准）
  → 后端 WidgetState.Set → 用"位置 + 本地歌词行 + offset"算出当前行 line
  → SSE lyric-state 广播（带 line）→ 桌面/安卓显示层 setText(line)（纯渲染）
```
- 优点：
  1. **逻辑一份**（后端的"位置→行"算法），桌面/安卓显示层**删本地算行**，改纯渲染。
  2. **链路短**（1 跳 SSE 直达），不绕 4 跳。
  3. **前端不活着后端还能算**（位置快照缓存在 WidgetState，切歌/暂停都能定位）。
  4. **不轮询**：SSE 推送（符合用户"废轮询要推送"）。
- 代价：后端要能拿到"位置 + 歌词行"——位置来自前端 POST 的快照（已有），歌词行来自
  后端自己的 `/music/lyric`（已有），**都是现成数据，不算新逻辑**。

**决策**：选 **B（后端算行 + SSE 推送）**。"播放位置在前端"不矛盾——前端**本来就上报位置快照**
（`/widget/state`），后端拿着位置 + 本地歌词行算行，逻辑仍是一份（后端的定位算法）。

## 三、统一架构（目标态）

```
┌──────────────────────────────────────────────────────────────┐
│ 播放位置源（谁在播谁上报）                                     │
│   · web 播放器 audio.currentTime → 前端 /widget/state（低频快照）│
│   · 位置快照缓存在后端 WidgetState（前端不活着也不丢）           │
└───────────────┬──────────────────────────────────────────────┘
                │ 位置 + 歌词行 + offset（后端本地数据）
┌───────────────▼──────────────────────────────────────────────┐
│ 后端算行（唯一"位置→当前行"逻辑，一份 Go 代码）                 │
│   WidgetState.Set(快照) → 算当前行 line → BroadcastLyricState │
└───────────────┬──────────────────────────────────────────────┘
                │ SSE /api/v1/widget/events  event: lyric-state
                │   data: { bvid, current_time, playing, line, ... }
      ┌─────────┼──────────────────┬──────────────────────┐
      ▼         ▼                  ▼                      ▼
 桌面挂件    安卓悬浮窗         web 字幕条              （未来其他端）
 (GTK)      (Java)            (JS)
 setText(line)  setText(line)  自己算(在前端,直接)   显示层纯渲染
 纯渲染        纯渲染          (唯一例外,在前端进程)   删本地 pickLine
 删 pickLine   删 pickLine
```

**分层原则（用户理念）**：
- **逻辑一份** = 后端"位置→行"算法（Go，一处）。
- **前端 UI 适配** = 显示层各自渲染（桌面 GTK / 安卓 TextView / web DOM），**不写算行逻辑**。
- **特殊接口适配** = 安卓授权（`canDrawOverlays` / `SYSTEM_ALERT_WINDOW`）、桌面穿透/置顶，
  各端自己接，**不污染统一逻辑**。

**唯一例外**：web 字幕条在前端进程里，直接读 `audio` 自己算（不用绕 HTTP），这是"在前端
就近"的合理特例，不算"逻辑写两份"。

## 四、SSE 推送（不轮询）——现状已落地

| 项 | 状态 |
|----|------|
| 后端 `WidgetState.Set` → `BroadcastLyricState`（SSE `lyric-state` + 完整快照） | ✅ 已提交（`cdda4e1`） |
| SSE 通道带事件名 + payload（`SSEMsg{Name,Data}`） | ✅ 已提交 |
| 桌面挂件 `listenEvents` 订阅 `/widget/events`（删 900ms 轮询） | ✅ 已提交（`cdda4e1`） |
| 安卓悬浮窗 `sseLoop` 订阅同一流（删 500ms 轮询） | ✅ 已提交（`44f0d21`） |
| 前端 250ms 上报位置快照（`/widget/state`，对齐 web timeupdate） | ✅ 已提交（`9641a7b`） |

**SSE 链路验证**：`POST /widget/state`（海阔天空）→ 订阅收到 `event: lyric-state`
+ `data:{"bvid":...,"current_time":12.5,...}`。

**"位置→行"还没进 SSE payload（本次要补）**：现在 `lyric-state` 只带 `current_time`，
显示层拿位置**自己算行**（= 三份逻辑）。本次要补：后端算好 `line` 塞进 payload。

## 五、本次代码改动清单（待做）

### 后端（`go/internal`）
1. `service/widget/widget.go`：`Set` 时算当前行——
   - 用**位置快照**（`BVID`/`CurrentTime`/`Playing`）+ **歌词行**（注入 `Lyric` service）+
     **offset**（`Lyric.Get(bvid).Offset`）算出 `line`。
   - 行定位算法（一份）：`for k { if sec <= ct+offset { idx=k } else break }`，
     对齐 web `subtitle.js`/`lyric.js`（`sec <= t` 找最后一行，KTV 进度由行 `dur` 字段）。
   - 切歌（`bvid` 变）→ 拉一次 `/music/lyric` 行缓存到 WidgetState（**低频**，不每帧拉）。
   - 广播 `lyric-state` 带 `line`（`SSEMsg.Data` JSON 加 `line` 字段）。
2. 注入 `Lyric` service 到 WidgetState（构造依赖），或算行算法独立成纯函数
   （`pickLine(lines []LrcLine, at float64) string`，**一处**，桌面/安卓显示层删本地版）。

### 桌面挂件（`wails3/widget/widget.go`）
3. `applyState` 直接用 SSE payload 的 `line` → `st.currentLine = line`，**删 `displayIdxLocked`
   / `st.lines` / `st.curIdx` 的本地行定位**（改纯渲染 `st.currentLine`）。
4. 歌词行宽（`fixLyricWidth`）：切歌时后端算好"最长行"也可带 `maxWidth`，或显示层按
   `line` 估宽（UI 适配，不算逻辑）。

### 安卓悬浮窗（`LyricOverlayService.java`）
5. `applyState` 只 `lyricView.setText(line)`，**删 `cachedLines` / `pickLine` / `fetchLyric`**
   （行数据全由后端 SSE 带，Java 端不拉 `/music/lyric`）。
6. **UI 适配（用户要的"补"）**：
   - **点击交互**：TextView `setOnClickListener` → 切播放/暂停（POST `/api/v1/music/pause`
     或对应端点；**特殊接口**，不污染逻辑）。
   - **极简控制条**（可选）：⏸ 按钮悬浮窗内（UI 适配，复用桌面按钮语义）。

### web 字幕条（`go/web/assets/subtitle.js`）
7. **保持自己算**（在前端进程，就近）；但**行定位算法与后端对齐**（`sec <= t` + KTV dur），
   避免"同一首歌 web 和挂件显示不同行"。

## 六、接口契约（前后端 / 显示层）

### `GET /api/v1/widget/events`（SSE）
```
event: lyric-state
data: {"bvid":"BV..","current_time":12.5,"duration":300,"playing":true,
       "title":"海阔天空","artist":"Beyond","line":"天空海阔","max_width":360}
```
- **`line`** = 后端算好的当前歌词行文本（唯一逻辑产物）。
- **`max_width`**（可选）= 本歌窗口宽（切歌定死，播放中不变，对齐 web 字幕面板固定宽）。

### `POST /api/v1/widget/state`（前端上报位置快照，低频 ~250ms）
```
{"bvid":"BV..","title":"..","artist":"..","current_time":12.5,"duration":300,"playing":true}
```
- 前端只报**位置**，不报 `line`（line 后端算）。

### 显示层消费
- 桌面 `applyState`：`st.currentLine = p.Line`（不再本地 pickLine）。
- 安卓 `applyState`：`lyricView.setText(p.Line)`（不再本地 pickLine）。

## 七、验证（验收标准）

1. **单测**：后端"位置→行"纯函数（`pickLine`）——给固定歌词 + 几个时间点，断言返回正确行。
2. **SSE 链路**：`POST /widget/state`（海阔天空, ct=12.5）→ 订阅 `lyric-state` 带
   `line`（非空、对应当前行）。
3. **桌面**：播放时挂件显示"后端算的 line"，切歌/暂停即时更新（不轮询）。
4. **安卓**：悬浮窗 `setText(line)`，**删本地 pickLine 后**仍正确显示；点击切暂停。
5. **一致性**：同一首歌、同一 `current_time`，web 字幕条 / 桌面挂件 / 安卓悬浮窗显示**同一行**。
6. **前端不活着**：关 WebView，挂件仍能按缓存快照 + 歌词行定位（方案 B 的优势）。

## 八、踩坑 / 已定结论

| 坑 / 结论 | 说明 |
|----------|------|
| **逻辑别写多份** | 三份本地 pickLine = 反复适配，必漏。一份在后端，显示层纯渲染。 |
| **前端算行够不着独立显示层** | 桌面/安卓是独立进程，前端 POST 绕 4 跳 + 高频 + 前端不活就死。后端算更稳。 |
| **SSE 不带行 = 伪统一** | 只推 `current_time`、让显示层自己算 = 逻辑还是散的。SSE 必须带**算好的 line** 才算真统一。 |
| **切歌才拉歌词行（低频）** | 行数据不每帧拉；切歌（bvid 变）拉一次缓存，逐帧只读缓存算 idx。 |
| **KTV 进度由行 dur** | `lines[i] = [sec, text, dur]`；dur 缺失用"下一行 sec - 当前 sec"兜底（对齐 web lyric.js）。 |
| **offset 只首载应用** | 用户对齐偏移 `Lyric.Get(bvid).Offset`，算行时 `t = ct + offset`（对齐 web）。 |
| **UI/特殊接口各端适配** | 安卓点击/授权、桌面穿透/置顶 = 各端自己接，不污染统一行定位逻辑。 |
| **web 就近特例** | web 字幕条在前端进程直接算（同一套算法），不算"写两份"。 |
| **正常 debug 编** | 不做 release 体积优化（用户明确）。 |

---

## 九、落地顺序（按提交切分）

1. **后端算行 + SSE 带 line**（`service/widget` + 注入 `lyric`）+ 纯函数 `pickLine` 单测。
2. **桌面挂件改纯渲染**（`applyState` 用 `line`，删本地 pickLine）。
3. **安卓悬浮窗改纯渲染 + 点击交互**（删 Java pickLine，加 click）。
4. **web 字幕条算法对齐**（确认 `sec<=t` + KTV dur + offset 与后端一致）。
5. 全端一致性验收（同一 ct 三端同显一行）。

> 原则：**逻辑一份（后端）→ 前端 UI 适配 → 特殊接口适配**。SSE 推送，不轮询。
