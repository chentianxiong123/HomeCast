# 音箱控制面降级——参考项目对齐与"深入控制打法"实验归档

> 日期：2026-11-13
> 决策：彻底降级。控制面做到 MiAir / xiaomusic 到达的程度即可；"深入控制打法"（分片喂流/实时热切换/本地改流）归档为实验，不再做。
> 性质：决策 + 探索归档

---

## 一、决策结论（先摆结论）

1. **控制面目标 = 对齐两个参考项目的能力**（见第二节），不再追求"播放中本地改流/热切换无感"那套深入打法。
2. **深入控制打法全数归档为实验**：曾经部分成功过（0.25s 分片无卡顿、spkmock 40 次零断流），但**代码已丢（streamtest 在 /tmp 清理时删除，git 无存档），复现不了，回不去了**。
3. **铁证级认知保留**（写死在文档里，后人不用重踩）：206 分片=毒（电磁音）、全量 200=稳定、操控=投新 URL 重新拉流。

---

## 二、参考项目控制面能力盘点（降级目标）

### 2.1 MiAir（DLNA 渲染器方案，/mnt/shared/ref-project/music/MiAir）

`miair/speaker.py` SpeakerController 全部能力：

| 能力 | 方法 | 说明 |
|------|------|------|
| 播 URL | `play_url()` | `play_by_url` / `play_by_music_url` 分支 |
| 暂停 | `pause()` | 部分型号用 `player_stop` 冒充 pause（API 状态不更新 workaround）|
| 停止 | `stop()` | stop + pause 双保险 |
| 音量 | `set_volume()` / `get_volume()` | - |
| 状态 | `get_status()` | status: 0=stopped, 1=playing, 2=paused |

**没有**：next/prev、seek、进度条、自动切歌、队列。（grep 确认无 next/previous/seek）

### 2.2 xiaomusic（队列管理方案，/mnt/shared/ref-project/music/xiaomusic）

`device_player.py` DevicePlayer + `api/routers/device.py`：

| 能力 | 方法/路由 | 说明 |
|------|-----------|------|
| 播 URL | `GET /playurl` → `play_url()` | 直接投 |
| 点歌 | `play()/play_music()` | 搜索→下载→播 |
| 下一首/上一首 | `play_next()/play_prev()` | 队列取曲 → 重新 `_play` |
| 播本地 | `playlocal()` | - |
| 自动切歌 | `set_next_music_timeout(adjusted_sec)` | **本地定时器**：`歌曲时长 + delay_sec − 获取耗时`，到点自动播下一首（对"音箱播完断流"的唯一处理）|
| 预缓存下一首 | `prefetch_next_song()` | 播 20s 后后台预下载 |
| TTS | `playtts` | - |
| 音量 | `setvolume/getvolume` | - |
| 状态 | `getplayerstatus` | status + volume + position/duration |
| 熔断 | `_play_failed_cnt >= 5` | 连续失败 5 次停播告警 |

**关键认知**：xiaomusic 的"自动切歌"**不是本地改流**，而是**歌播完（定时器判定）→ 重新 play_by_url 下一首**。它从没碰过：seek、播放中本地暂停、分片喂流、进度真实消费确认。

### 2.3 对齐后的控制面（我们的目标形态）

```
播放    = 投 URL（play_by_url）✅ 已有（PlayURL 端点）
暂停    = 断源 / 投静音          ✅ 已通（降级：按 xiaomusic 用 player_stop 或直接停）
音量    = player_set_volume       ✅ 已有
切歌    = 重新投 URL              ✅ 已有（play_url 换 URL）
自动下一首 = 本地定时器（时长+补偿）→ 到点投下一首   ← 对齐 xiaomusic，落地即可
进度    = 乐观计时（像 xiaomusic 的 get_offset_duration：time−start）  ← 不做真实消费确认
seek    = 不做（参考项目也没有）        ← 降级取消
```

## 三、"深入控制打法"实验归档（不再做，但记录为什么）

> 三个多月一路试下来的完整打法，逐条留档。**成功过的代码已丢，复现不了**。
> 唯一还活着的：`go/cmd/mock/spkdemo`、`go/cmd/mock/spkmock`（2026-11-13 归拢保留，但只是实验台，不是生产控制）。

### 3.1 打法演进时间线

| 阶段 | 打法 | 结果 |
|------|------|------|
| 早期 | 全量 200 一次给 | 稳，但操控=不可控（播缓存，改不了）|
| 二分法找分片阈值 | 0.5s/12KB、0.25s/6KB 分批喂 | **streamtest 实测无卡顿，代码在 /tmp 已丢** |
| 877KB 预缓冲发现 | 分片让解码器常空→切源即时 | 平滑陷阱：全量=切源 54.8s |
| 长连接慢喂 | 0.5s/片、预缓冲后转实时 | 音箱 2s 读超时 broken pipe，证伪 |
| CDN Range 206 | 短连接 Range 续传 | **乱序拉头/尾→喂非音频字节=电磁音**，封杀 |
| 全量 200 复活 | 真歌全量 | 稳（用户双耳确认），但操控又回到"只能云重投" |

### 3.2 决定性铁证（保留给后人）

```
1. 206 分片对这台音箱是毒：
   rangetest.log：音箱同秒乱拉「0-16383」+「2871873-2872000(文件尾128B)」+ 再「0-」
   → 尾 128B = mp3 ID3/填充非音频字节，当音频解码 = 电磁音风暴（用户现场暴怒）
2. 全量 200 = 稳定干净：
   静音流 12:03:56-58 连拉 4 份全量，0 断流 0 噪音，之后 25 分钟不再拉（播缓存）
   真歌 mp3 12:45:11-14 连拉 5 份全量，用户："现在是稳了"
3. 判断声音不能看拉流次数：0 次拉流有声（播缓存）；一堆拉流没声（解码失败反复拉）。
   正确测量 = URL 每次带 v=时间戳逼音箱重新拉流
4. 操控唯一通道 = 云 play_url 下指令 + 新 URL（v=时间戳）重投 → 音箱重新拉新内容
5. 长连接慢喂（0.5s/22KB）→ 音箱 2s 读超时断（broken pipe）→ 该喂法已放弃
```

### 3.3 曾经成功、现在回不去的东西

| 成果 | 证据 | 现状 |
|------|------|------|
| streamtest 分片喂流（0.25s 无卡顿）| 11-10 文档：二分法实测表 | **代码 `/tmp/streamtest` 已随 /tmp 清理，git 无存档** |
| spkmock 假音箱（40 次顺序拉流零断流）| 2026-11-13 实测 | 代码还在 `go/cmd/mock/spkmock` |
| 进度 = 音箱真实消费字节（RecordLoaded）| 但统一端点后无人调用 | 永远走本地时钟 → 进度无限涨，未修 |
| 热切换无感（稳定供流+喂速=实时）| 11-10 待验证假设 | **证伪**：预缓冲 2s 后照样 broken pipe |
| seek = 新 URL 虚拟文件 0 映射 | 方向成立 | 未落地；参考项目也没 seek，降级取消 |

### 3.4 为什么"不做了"

1. 音箱是固件黑盒：稳（全量）与可控（≤2s）**互相矛盾**，试尽所有中间态（分片大小/慢喂/预缓冲/206）全部翻车或不可控。
2. **成功过的代码丢了**：streamtest（唯一验证过 0.25s 无卡顿的实现）在 /tmp 清理时删除，且从未进 git——**已经回不去了，复现=从零重写，且没有任何方向保证**。
3. 参考项目（xiaomusic/MiAir）证明：**不做深入控制也活得挺好**——它们就是"投 URL + 定时器自动切歌"，用户照常用。
4. 单功能逐项可交付，投入产出比最高：把已有的 PlayURL/音量/切歌+定时器连起来，就达到参考项目水平。
