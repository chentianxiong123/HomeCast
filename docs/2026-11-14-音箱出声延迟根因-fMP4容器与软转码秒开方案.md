# 音箱出声延迟根因定位：fMP4 容器格式 + 软转码 mp3 秒开方案

> 探索留档（explore/speaker-latency-mock）。记录一次"真系统点播放到音箱出声三四秒"
> 的黑盒定位全过程。结论可落地，但 mock 代码本身不引用进主程序。

## 一、问题

真系统（HomeCast 后端投小米音箱）从**点播放**到**音箱真正出声**，稳定延迟三四秒。
一直不知道瓶颈在哪：是命令下发慢？网络慢？音箱硬件慢？还是取流慢？

之前一直没认真测——凭感觉猜。这次决定用**真实音箱做黑盒对照实验**，把每个变量拆开量。

## 二、方法论：独立 mock，逐变量拆解

不污染主程序，在 `/tmp` 起独立 mock（后迁入 `explore/speaker-latency-mock/`）：

- 用真实音箱 token（`~/.config/homecast/speaker.json`）+ miservice 库，对真实音箱下发 `player_play_url`
- mock 自己起一个流服务器，音箱拉的是 mock 的 URL → **mock 精确知道音箱"何时开始拉流"**
- web 测试台（`:28777`）实时显示：命令下发时刻 / 音箱首次拉流时刻 / 动态延迟 / 累计拉流次数 / 已喂字节
- 关键：**音箱拉的始终是"我们的流"**，想喂什么格式、什么内容由 mock 控制 → 可做对照

打点精度到毫秒（`time.Now().UnixMilli()`），避免秒级日志看不清 sub-second 差异。

## 三、实验过程（四轮，逐步逼近根因）

### 第一轮：本地静音/正弦 tone → 延迟极低

mock 最早喂的是**程序生成的连续正弦音（WAV PCM）**。

实测：命令下发 → 音箱首次拉流 = **153~457ms**（多组），且拉流次数少就出声。

结论：**命令下发→音箱拉流这一段极快**，瓶颈不在这。但当时喂的是 tone，不是真歌，
说服力不足 → 需要喂真歌再测。

### 第二轮：代理真 B 站 m4s → 发现"拉很多次才出声"

mock 改成代理真 B 站：`/audio/{bvid}` 收到音箱拉流 → mock 取 B 站 playurl 拿 m4s 直链
→ 带 `Referer` 转发给音箱（B 站 CDN 防盗链，无 Referer 返回 403）。

喂真歌（七里香 BV1ciWb6yEWW）后，web 台出现反常数据：

```
累计拉流 25 次 / 已喂字节 6.1MB 才开始唱歌
```

而这首歌 m4s 总共才 3.1MB。**6.1MB > 整首大小** → 一开始以为是 mock 计数重复。

### 第三轮：关键对照——mp3 vs m4s（根因水落石出）

为排除"是不是 mock 计数重复"，把**同一首歌**转成两种格式分别喂：

| 喂流格式 | 出声前累计拉流 | 出声前已喂字节 | 出声 |
|----------|--------------|--------------|------|
| **fMP4 / m4s** | 48 次 | 13.2MB | 拉满几乎整首才出声 |
| **mp3** | **3 次** | **1.9MB** | **瞬发** |

同一首歌、同一音箱、同一命令链路，**只换音频容器格式**，结果天差地别。

**根因确认**：
- **fMP4/m4s** 是分片容器，音箱必须先拿到 `moov` 元数据头 + 攒够**连续可解码的 sample 片段**，
  才能开始解码出声 → 要拉很多次、累积大量数据
- **mp3** 是流式帧格式，音箱拿到第一段（~1.9MB）就立刻能解码 → 瞬发

**所以"三四秒延迟"的根源 = B 站音频源是 DASH/fMP4(m4s) 格式**，跟命令下发、网络、
音箱硬件全都无关。这也解释了为什么之前怎么优化命令链路都没用。

### 第四轮：软转码 mp3 → 秒开方案

既然根因是格式，解法就一个：**喂音箱前把 m4s 转成 mp3**。

#### 软转码可行性
- ffmpeg `libmp3lame` 纯 CPU 软编（MP3 无广泛硬件编码器）
- 转一首 3.8 分钟的歌只要 **3.4 秒**（几十倍实时），边播边转绰绰有余
- **不需要硬解**：AAC 解码极轻量，MP3 编码也只能软编，硬解要配驱动/权限/平台差异，音频场景收益为零

#### 踩坑 1：ffmpeg 直连 B 站 403
最初想让 ffmpeg 直接从 B 站 m4s URL 拉流转码，结果 **403 Forbidden**。
排查：加 Referer、修 buvid3 格式（字面占位符 `xxxxxxxx` 会 403，要合法 UUID）都不行——
**ffmpeg 的 HTTP 实现（默认 UA / icy-metadata 请求）触发 B 站防盗链**，而 Go `net/http`
带 Referer 能正常下。**绕开**：用 Go 下载 m4s 到本地，ffmpeg 只做本地文件转码。

#### 踩坑 2：写音箱与写缓存耦合 → 卡死
第一版"边转边喂"把"写给音箱"和"写缓存"放同一线程：音箱拉够一段就**停止拉流**开始放歌，
mock 还阻塞在"写给音箱" → 转码 goroutine 卡死 → 缓存永远写不完。
**解法**：转码 goroutine 独立跑完 ffmpeg 并完整落缓存（不被音箱拉流节奏卡住）；
音箱只管拉它的，拉够停拉不影响转码落盘。

#### 最终方案：边转边喂 + 缓存
```
B站 m4s →(Go下载)→ 本地m4s →(ffmpeg)→ mp3 流 ─┬─→ 实时推音箱（拉到第一段即出声）
                                              └─→ 写 mp3 缓存（后台落盘）
```
- **首次播放**：命令后 ~1 秒出声（首个 mp3 字节 878~1266ms），不用等整首转完
- **同曲二次播放**：命中 mp3 缓存，**秒发**（连 1 秒都不用）
- 音箱停止拉流后，转码后台继续跑完落缓存，互不阻塞

## 四、最终结论

| 项 | 结论 |
|----|------|
| 三四秒延迟根因 | B 站音频源 fMP4/m4s 容器格式（音箱解码 fMP4 需缓冲期），**非命令/网络/音箱** |
| 解法 | 喂音箱前软转码成 mp3（流式格式） |
| 转码性能 | ffmpeg `libmp3lame` 纯 CPU，3.8 分钟歌转 3.4 秒，几十倍实时，**无需硬解** |
| 出声延迟 | m4s 拉满整首 → mp3 首次 ~1s / 二次秒发 |
| 落地要点 | ffmpeg 本地转码（绕 B 站 403）+ 转码与喂流解耦（防卡死）+ mp3 缓存（二次秒发） |

## 五、附带发现（探索过程中的支线）

1. **进度模拟的锚定**：因进度是本地模拟时钟，命令→拉流有延迟，需在**音箱首次拉流到达时刻**
   锚定进度基准（`AnchorStream`），否则进度虚增这段延迟。锚定前进度凝固在目标基准不虚跑。
2. **音箱是"一次性缓冲"黑盒**：拉满一段缓冲就停拉流、开始放；播完已缓冲的才回来继续拉。
   切源只在它恢复拉流时生效 → 同 URL 续喂切源不可行，必须重新下发命令。
3. **多设备停止要按 did 精确停**：mock 早期 `/api/stop` 写死"停第一个在线设备"，
   两台在线时停错设备 → 暂停失效。改为按选中 `device_id` 精确停。
