# 框架与架构优异性论证：Go 单二进制 + htmx 片段 + 业务域包

> 日期：2026-10-17　作者：HomeCast 项目作者
> 定位：不是踩坑记录，是**选型与架构的优越性论证**——为什么这套组合好、好在哪、证据是什么、代价是什么。
> 配套：模板残缺踩坑详见 `2026-10-14-Golang-HTML模板残缺问题排查与治理.md`，本文第 ③ 章并入其要点。

---

## 一句话论点

**Go（单二进制内嵌一切）+ htmx（服务端渲染片段）+ SQLite（无进程）+ 业务域包（垂直切片）** 的组合，让一个三端应用（Linux/Windows/安卓壳）**只产出一个 25MB 二进制**，浏览器端**零构建、零依赖、零版本碎片**，后端代码**改一个业务只动一个域包**。这不是"能用"，这是单人全栈能长期维护的最小复杂度方案。

---

## ① 框架选型：四个"为什么"

### 1.1 为什么是 Go —— 部署物是一个文件

```bash
$ ls -la bin/hcexp-linux
-rwxr-xr-x 25M  # 业务核心 + htmx 前端 + SQLite + 模板 + 静态资源，全在这一个文件里
```

- `go:embed` 把 **15 个模板 + 全部静态 JS/CSS** 编译进二进制——磁盘上只有这个文件
- SQLite 用 `modernc.org/sqlite`（纯 Go 驱动）——**无 CGO、无独立数据库进程**
- 音箱/投屏协议是纯 HTTP 客户端——不依赖系统组件
- 结果：**部署 = 拷一个文件 + 跑起来**。没有 Node、没有 Nginx、没有 Redis、没有环境变量矩阵

### 1.2 为什么是 htmx —— 前端没有构建链

对比前端三件套（Node + Vite + npm 依赖树），htmx 方案：

| 维度 | Vue/React SPA | htmx + 服务端片段 |
|---|---|---|
| 构建 | Vite/npm 依赖树 | **零构建**（htmx.min.js + alpine.min.js 两个文件） |
| 状态 | 前端 store 同步后端 | **服务端是唯一事实源**，`hx-get` 拉片段即渲染 |
| 接口 | REST 双写（前端 DTO + 后端 DTO） | 片段模板就是"接口"，`/hx/*` 直接出 HTML |
| 升级 | 依赖版本碎片 | 无依赖可碎 |
| 可维护 | 前后端两份代码 | **一份 Go 代码管数据 + 渲染** |

HomeCast 实测：**api（JSON，给音箱/自动化用）+ hx（htmx 片段，给浏览器用）双入口共用同一批域包**——同一份业务逻辑，两种出口，零重复实现。

### 1.3 为什么是 SQLite —— 数据随包走

- 无独立 DB 进程 → 三端壳（Linux/Windows/安卓）数据目录各自 `~/.config/homecast/`
- 幂等迁移 `store.Migrate`：**表定义在业务域包，执行集中，首启从旧 JSON 导入**——拆表定义后老库数据零损失（实测 `favs/playlist/lyric_sels` 三表完好）

### 1.4 为什么三端共用业务核心 —— 壳是薄壳

```
go/ 业务核心（一个端口跑全部：服务端 + htmx 前端 + SQLite）
     ↑ 三端共用
wails3/ 薄壳：WebView 直载 htmx + 挂件显示层（GTK/Win32）+ 平台差异 build tag
```

业务永远只写一份；壳只做"开窗"（WebView）和"显示歌词"（挂件）。**换壳不换脑**。

## ② 模板防线（htmx 架构的必备安全网）——并入要点

**htmx 的核心玩法是渲染 HTML 片段**，这正是 Go `html/template` 的盲区：

> **Go `html/template` 只校验 `{{}}` 语法，完全不检查 HTML 标签闭合；浏览器 HTML5 容错解析会自动修复残缺标签。** 两个"不报错"叠在一起 = 残缺模板能潜伏 12 天，页面"看起来能用，实际布局全错"。

（完整踩坑过程、最小复现、htmlhint 误报细节见 `2026-10-14-...` 文档。）

**防线四层（已全部落地，实测可用）**：

| 层 | 手段 | 实测证据 |
|---|---|---|
| 1 | `grep -oE '<div[^>]*>' \| wc -l` 数开闭 | 一眼看出不平衡 |
| 2 | **Go 单测正则** `TestTemplatesHTMLBalance` | `go test ./web/` 0.006s 扫 15 模板，残缺精确报文件名+标签 |
| 3 | HTMLHint 命令行（`.htmlhintrc` 关掉模板误报项） | 报错精确到行号 |
| 4 | **git pre-commit hook**（`scripts/pre-commit.sh`，`core.hooksPath` 安装） | 残缺模板进不了库（注意 `set -e` 在管道不生效，必须 `pipefail`） |

**三合一模板测试现状**（`web/templates_test.go`）：

```bash
$ go test ./web/ -run TestTemplates -v
=== RUN   TestTemplatesParseSyntax   # {{}} 语法全模板可解析
--- PASS
=== RUN   TestTemplatesHTMLBalance   # 块级标签开闭平衡
--- PASS
=== RUN   TestTemplates              # 模板函数渲染不炸（FuncsRender）
--- PASS
```

结论：**"内嵌 + htmx"不是裸奔**——内嵌不影响工具扫源文件，防线齐了就是安全网。

## ③ 架构优异性：业务域包垂直切片

（内聚四步已落地，完整过程与踩坑见 `2026-10-17-架构探索与内聚化经验.md`，本文只讲"为什么优越"。）

### 3.1 一个业务 = 一个域包 + 两处薄胶水

```
改「音箱音量渐变」时你只碰：
  internal/service/speaker/      ← 逻辑 + SQL + 表定义 + 测试（全在这）
  internal/api/speaker.go        ← JSON 出口（薄胶水）
  hx/speaker.go                  ← htmx 出口（薄胶水）
  web/templates/speaker_*.html   ← 前端
其它 8 个域包一个都不用开。                  ← 这是优越性：改动半径=业务半径
```

### 3.2 五个被实战验证的优越点

1. **依赖 DAG 无环**（编译期保证）：`music→lyric`、`sites→cast`、`speaker/cast→token`，其余独立——拆包手术零返工，改完即绿
2. **表定义跟业务走**：`favs` 的 schema 在 `service/fav/fav.go`，改收藏表结构不用翻 store
3. **测试跟业务走**：域包自带测试（speaker 4 用例 / lyric 4 文件 / fav / playlist / music），`go test ./...` 12 包全绿
4. **地图注释**：每个域包文件头一行"职责 + 入口 + 前端 + 表"，新人（或三个月后的自己）5 分钟定位任何业务
5. **纪律文档化**（README）：新逻辑进域包 / SQL+表定义跟业务 / 域包自测 / 薄胶水入口——防回潮

### 3.3 为什么"接口层"不要（反直觉但正确）

模板建议 business/infra/glue 三层 + 接口层。HomeCast 论证后**不做接口层**：
- 单人单实现，接口 = 空转（唯一第二实现是 `LyricStore db==nil` 内存兜底，一个特例不值得铺一层）
- **Go 的鸭子类型 + 薄胶水已经给出足够替换点**——换实现只动胶水，不动域包

| 指标 | 数值 | 说明 |

| 老库迁移 | 三表完好 | 拆表定义/拆包后数据零损失 |

## ⑤ 代价与适用边界（诚实）

**这套架构不是银弹，代价要认：**

| 代价 | 说明 | 缓解 |
|---|---|---|
| 模板残缺隐患 | Go 模板不查 HTML 结构 | 四层防线已补（见 ②） |
| 片段粒度难复用 | 组件化弱于前端框架 | 规模 < 30 模板够用，> 50 评估 templ |
| 交互上限 | 复杂 SPA 交互不适合 htmx | 本项目交互 = 列表/表单/进度轮询，恰好在舒适区 |
| 双入口双写 | api + hx 两处胶水 | 薄胶水只做"取数→渲染"，业务零重复 |
| 单人视角 | 没验证过 5 人团队协作 | 域包边界即职责边界，理论上利于分工 |

**适用边界一句话**：**服务端渲染能表达的交互（CRUD、列表、表单、轮询进度），这个组合是最低维护成本方案；纯前端动画/复杂状态机，别用它。**

---

## ⑥ 结论

- **框架优越**：25MB 单文件、零前端构建、SQLite 无进程、三端共脑
- **架构优越**：域包垂直切片 + 双出口薄胶水 + 表/测试/注释跟业务走 + 纪律文档化，**改动半径 = 业务半径**
- **安全网**：模板四层防线让 htmx 片段渲染没有裸奔风险
- **证据**：全部是实测数字（12 包绿 / 11 端点 200 / 15 模板 3 防线 / 老库无损）

> 折腾到现在的结论：**这不是"最潮"的架构，是"最少需要维护"的架构。** 对一个单人全栈、三端出活、且会长期迭代的项目，这就是优异性。
