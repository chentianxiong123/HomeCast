## 二、🔴 高风险区（动过核心播放路径，已爆 bug）

### 1. 音频缓存落盘重构 `b5a2004`

| 问题 | 状态 |
|------|------|
| `StreamAndCache` 只判 `n>64KB` 就落盘 → 下载中断存**截断文件** → seek 超范围 416 → 跳末尾误切歌 | ✅ 已修 `b99ce0c`（Content-Length 校验，只有 `n==contentLength` 才落盘） |
| **无内容 hash**——文件损坏（非截断）检测不到 | ✅ 已修 `2b8cd1c`（audio_cache 加 hash 列：文件头 4KB FNV-1a 低31位 + 幂等 ALTER；Put 落盘写 hash，Get 不符即删缓存重拉） |
| `.tmp` 残留（进程被杀，StreamAndCache 未走完 Remove(tmp) 的孤儿） | ✅ 已修 `2b8cd1c`（启动 cleanupTmp 清 *.tmp） |
| **遗留**：Range/206 请求不缓存 → 拖动进度条后续播有时回源 | ⚠️ 设计取舍（可接受：缓存命中即本地 serve 支持 Range） |
| **遗留**：`Get()` 完整性校验与 `Put()` 写实际大小逻辑冗余 | ⚠️ 逻辑冗余（无功能风险） |
| LRU 淘汰 / `ClearExpired` 与正在写入的流**竞态**（边写边被删） | ✅ 分析自洽：写 .tmp → rename → Put(持锁)，ClearAll 删 .tmp 仅致缓存丢弃，无数据损坏 |

**根因**：tee 落盘时浏览器 seek/切歌断连 → `io.Copy` 提前返回 → 截断文件被当有效缓存。
**教训**：流式落盘必须校验完整性，不能只看字节数阈值。

### 2. 状态统一重构（4 阶段 `9b935fc`→`62b5fa4`）

| 问题 | 状态 |
|------|------|
| `player.js` 阶段2 大改（删业务状态 + Alpine + SSE 桥）→ **切歌瞬间 store duration 滞后** → 显示卡死 3:04 | ✅ 已修 `bc0fdd7`（web 模式 audio.duration 优先） |
| **音箱模式仍用 store duration**（SSE 推），可能同样滞后 | ✅ 已修 `2b8cd1c`（queue duration 全链路传递 + 播放后真实时长回写 queue；音箱切歌用 queue[k].Duration） |
| **seek()** 用 `audio.duration \|\| pb().duration`——audio 元数据没加载完时回退到可能为 0 的 store，seek 算错 | ✅ 已修（d<=0 直接 return 防算错；sec>=d 防越界音） |
| **queue 持久化里所有歌 `duration=0`**（数据质量缺陷），影响歌词定位/时长预估 | ✅ 已修 `2b8cd1c`（结果/收藏/全部播放/右键/插队入口全部带 duration 入队；command body 加 Duration；播放后回写并持久化） |
| **多客户端同时 `POST progress`**（日志见每秒十几次）→ 互相覆盖 position，无时钟同步 | ✅ 已修 `2b8cd1c`（progress 上报带 bvid，后端不匹配当前播放歌则静默丢弃） |
| **遗留**：高频 timeupdate（250ms）上报 + SSE 广播，多客户端下**广播风暴** | ⚠️ 性能隐患（低频 250ms，暂可接受） |
| **遗留**：旧 localStorage→SQLite 迁移，格式不符可能丢队列 | ⚠️ 未充分测 |
| persistNow 频繁写 SQLite，快速切歌频繁 IO | ✅ 已缓解（SetProgress 只在 duration 变化时持久化） |

**根因**：Alpine store 是切歌瞬间的**滞后快照**，直接读会残留旧值。
**教训**：高频 UI（时长/进度）应优先读真实 DOM 状态（`audio.duration`/`audio.currentTime`），store 只作兜底。

## 六、根因总结

两天的问题集中在「**动了核心播放路径但没充分验证时序/完整性**」：

| 类别 | 表现 | 已爆 bug |
|------|------|---------|
| **完整性缺失** | 缓存落盘不校验完整性 | 点进度条切歌（截断文件 416） |
| **时序滞后** | 切歌瞬间读 store 残留旧值 | 切歌后时长卡死 3:04 |

**已修的两个 bug 都是这一类**。后续任何动核心播放路径的改动，都要先回答：
- 流式数据落盘/缓存——**完整性怎么校验？**
- 切歌瞬间——**前端读的是真实 DOM 状态还是滞后 store？**

## 七、验证方式

- 缓存修复：MCP 实测同首 5 次 seek（10/50/90/30/70%）全程无 ended、无切歌
- 时长修复：MCP 实测连续切 3 首，总时长各自正确（1:48 / 2:59 / 1:58）
