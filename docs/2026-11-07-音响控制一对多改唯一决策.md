# 音响控制架构决策：一对多 → 唯一（复用播放器面板）

日期：2026-11-07
状态：决策记录（一对多已放弃，改唯一）

## 背景

音响（小米音箱）推送播放需要控制面。讨论过程中出现两个方向：
- **一对多**：手机（主控）控制多个音响同时播放
- **唯一**：一个控制面（复用现有播放器面板）控制音响

## 探索过程（为什么要讨论一对多）

1. 用户最初提到"手机两个音响一起"——以为要一对多（多音响同时播）。
2. 排查发现当前 speaker 架构是**前端轮询自己的后端**（`/speaker/progress/{did}`），
   进度=服务端**本地时钟**算（`speaker.go` 注释：`// 零小米云轮询`、`// 不打小米云`）。
3. 用户确认：**不打小米云**，废前端轮询改 SSE。

## 关键决策

### 决策 1：SSE 单流（已实施，tag v0.18.0-gtk4）
- `SpeakerService.AllProgress()`：遍历所有设备进度（本地时钟 Position，stopped 跳过）
- `GET /speaker/events`：SSE 单流，1s 定时推所有音响进度 + 15s 心跳
- `speaker.js`：删 `setInterval(poll,1000)` 轮询 → `EventSource('/speaker/events')`
- 单测 `TestSpeakerAllProgress` PASS（mock 零网络）

### 决策 2：放弃一对多（多音响同时播）
理由：
- **多音响同步进度/控制复杂**：一台播放器面板显示哪台进度？多台状态合并？
- **多流模式用户不要**：用户明确"不要多流模式"，一对多需要每台状态流
- **复用播放器面板**：用户"直接复用播放器面板，不要鹤立独行"——一个面板控制，
  多音响同时播与"唯一面板"矛盾
- **成本/收益**：多音响同时播是边缘场景，复杂度高收益低

### 决策 3：改唯一（复用播放器面板）
- **唯一控制面** = 现有底部播放器面板（`player-dock`）
- 播放器面板复用：进度条 `d-progress` 显示音响进度，播放/暂停按钮控制音响
- 音响卡片（`speaker_devices.html`）只做**接入/推送选择**，不重复控制/进度
- 不做多音响同时播（唯一音响控制，或唯一面板控制当前推送音响）

## 待实施（唯一化）
