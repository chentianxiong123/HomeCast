### 2.2 音箱拉流行为（黑盒实测结构）

音箱是**被动 HTTP 拉流方**：我们用 API 下指令 → 云 → 音箱来我们局域网 HTTP 服务器拉流。**它自己发 HTTP Range 请求**，请求模式三种：

| 请求 | 含义 | 正确响应 |
|------|------|---------|
| `Range: bytes=0-` | 从头拉 | 全量内容（200）或一片（206）|
| `Range: bytes=<总长>-` | **文件尾探测**（判断文件是否变/大小是否对）| 必须回 **416** |
| `Range: bytes=<总长-128>-` | 读 mp3 尾 128B（ID3v1 标签）| 回尾部字节 |

### 2.3 缓存文件真相

- 缓存目录：`/home/a1/.config/homecast/cache/audio/*.m4s`
- ffprobe 取证：这些 `.m4s` **实为 MP4 容器 + AAC 编码**（BV1GJ41197fi.m4s 实测 `duration=108.38s bit_rate=60131`）
- 之前"m4s 解不了"的真正原因是 `Content-Type` 硬编码成 `audio/mpeg`；改回 `application/octet-stream` 让音箱自嗅探即可

## 五、踩坑记录（每条都是真机现场，按 现象→根因→解法）

### 坑 1【最高级】：206 分片喂非音频字节 = 电磁音风暴（用户暴怒现场）

- **现象**：用户耳朵现场暴怒："马上暂停流啊 好吵啊 全是电磁音 巨吵"
- **根因**（rangetest.log 铁证）：音箱 206 分片模式下**乱序拉**：同秒先从 `0-16383` 拉头，又**从文件尾 `2871873-2872000`（128B）拉尾**，再回头拉 `0-`。mp3 尾部 128B 是 **ID3/填充非音频字节**——把这当音频喂给解码器 = 电磁音；分片拼接错乱 = 断流/放一会就停
- **解法**：**206 分片模式对这台音箱一刀切封杀**。喂给音箱的内容必须是合法音频字节；宁可给静音帧也不给垃圾字节
- **铁证引用**：`/tmp/rangetest.log`：`206 range=bytes=0- → 0-16383` → `206 range=bytes=2871873- → 2871873-2872000` → 再次 `0-`

### 坑 2：判断"音箱有没有声"不能看拉流次数

- **现象**：0 次拉流 l 却有声（音箱播缓存）；一堆拉流反而没声（反复拉解不出的数据）
- **根因**：拉流次数 ≠ 播放成功。解码失败时音箱会疯狂重拉
- **解法**：URL 每次带 **v=时间戳** 参数，逼音箱重新拉流，用新连接判断真实行为

### 坑 3：长连接慢喂（0.5s/片、22KB/片）触发音箱 2s 读超时

- **现象**：`broken pipe`，连接 2s 就被音箱掐断
- **根因**：音箱对响应速率有期望，喂得慢（尤其连接建立后头 2s）它就判定死流
- **解法**：放弃长连接慢喂。**全量 200 一次给完**才是它买账的节奏

### 坑 4：v=时间戳重投时"虚拟文件总长缩水到 0"→ 断断续续

- **现象**：音箱刚拉开头就 416，重投循环，声音断断续续
- **根因**：spkdemo 曾在 `handleStream` 里"新 URL（v 变化）重置 basePCM = 当前进度"→ reconnect 每次发新 v → basePCM 反复前移 → total 从 2872001 一路缩到 0
- **解法**：**basePCM 只由控制指令（seek/切歌/play）设置，流请求绝不动它**；reconnect 判据从 1.5s 放宽到 10s（音箱拉一块 ≈8s 音频后正常静默播放 8s 才要下一块）

### 坑 5：预缓冲 877KB 是"平滑陷阱"（11-10 已证，本段再确认）

- **现象**：200 全量虽然稳，但音箱一次拉满，播 54.8s 才空 → 切换不可控
- **根因**：音箱解码器预缓冲 ≈877KB = 54.8s × 128kbps
- **解法**：接受"全量 = 稳但靠云重投控制"的现实——**操控不靠本地改流，靠投新 URL**

### 坑 6：进度无限涨（根因在代码）

- **现象**：进度条 316s > 歌长 108s
- **根因**：`speaker.go Position()` 的 `RecordLoaded` 是代理时代回调，统一端点后**从不被调用** → LoadedBytes 恒 0 → 永远走本地时钟
- **解法**：本质是"进度=音箱真实消费字节"的依赖断链；收尾时仍未改（见第八节未解之谜）

### 坑 7：Content-Type 硬编码 audio/mpeg 解不了 m4s

- **现象**：m4s 播不出声
- **根因**：m4s 是 MP4；audio/mpeg 是 mp3 的声明
- **解法**：改回 `application/octet-stream`（音箱自嗅探），或按扩展名给出正确类型

### 坑 8：播完不切歌（服务器端 hook 漏接）

- **现象**：一首播完一直放，不自动连播
- **根因**：`server.go` 里 `speakerSvc.EndedHook` 是 nil——timer 到点调了空 hook，什么都没做
- **解法**：接上 `EndedHook → playbackState.Next()`（本段已修复并部署）

### 坑 9：边缘行为——播完环境返回 416 而不是回 0 循环

- **现象**：serveSpeakerChunk 播完一直回 0 片 → 无限重放掩盖 bug
- **解法**：播完返回 **416**（`Content-Range: bytes */size`），音箱识别文件尾自然结束

```
206 range=bytes=0- → 0-16383
```

- 但 100KB 分片仍逃不过乱序拉头/尾 → 依然有毒

## 七、决策记录（含走不通的方向）

| 决策 | 理由 | 状态 |
|------|------|------|
| **206 分片 = 毒，全量 200 = 正解** | 乱序拉头/尾 + 非音频字节 = 电磁音铁证；全量 200 静音/真歌双验 0 断流 | ✅ 定案 |
| **操控唯一通道 = 云 play_url 下指令 + 新 URL（v=时间戳）重投** | 音箱播缓存不受本地控制；只有让它重新拉新 URL 才听话 | ✅ 定案 |
| **长连接慢喂/实时热切换（11-10 待验证假设）** | 2s 读超时 broken pipe；预缓冲 2s 后照样断 | ❌ 证伪 |
| **seek = 新 URL 时虚拟文件 0 映射到歌内目标位置** | 音箱只认"从头拉"，违反 Range 契约（0- 回别的起点）→ 无限重试 0- | ✅ 方向保留（未落地）|
| **Content-Range 必须如实** | 虚标 CL / 给 0- 回别的起点 → 音箱判定文件变了断开 | ✅ 定案 |
| **播完返回 416 不循环** | 避免无限重放掩盖 bug | ✅ 落地（hcserver）|
| **Content-Type 用 octet-stream 自嗅探** | m4s=MP4 硬编码 audio/mpeg 解不了 | ✅ 落地（hcserver）|
| **进度 = 音箱真实消费字节（RecordLoaded）** | 但从无人调用 → 恒走本地时钟 | ⚠️ 方向对，未落地 |

## 八、未解之谜 / 下一步岔路

1. **"全量 200 = 稳"与"操控 ≤2s"仍未兼得**：全量稳，但操控只能靠云重投；重投延迟 = 音箱固件 2-3s + 重新拉流。用户最终判定"太复杂的黑盒"，本段收尾。若要做：spkdemo 已按"全量 200 + 操作换 URL"重写完成（`-songs` 多曲/seek→serve 剩余段/暂停→静音源），但**未在真机上完成全链路验收**。
2. **进度条修复**：`RecordLoaded` 无人调用导致进度走本地时钟无限涨——需 serveSpeakerChunk 每片回报 end，播到 416 钳在 duration。
3. **多源浏览**：缓存 m4s（MP4+AAC）直接喂音箱未在 200 全量下真机验证（已转过的 /tmp/songs/*.mp3 是备用）。
4. **"播放中全本地控制"是否真不成立**：11-10 认为播放中暂停/切歌可全本地，本段实测音箱播缓存后本地改流无效——须重投。这块结论以本段为准。
