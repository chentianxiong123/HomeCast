# 2026-11-08 HomeCast 鸿蒙版：从编译签名到模拟器跑通（排查记录）

> 一句话结论：**成功的关键不是签名、不是端口、不是 ArkWeb、不是 Go 业务逻辑，而是修掉了原生库 `libentry.so` 里被写进去的 Windows 绝对路径（DT_NEEDED/RUNPATH）**。CMake 两个开关（`CMAKE_SKIP_RPATH` + `IMPORTED_NO_SONAME`）才是压轴解。

## 背景

HomeCast 的架构原则：业务逻辑一份住 Go 后端，前端复用 go:embed，前后端只走真实 HTTP（`http://127.0.0.1:28976`），各平台壳只负责窗口/WebView/系统能力。

鸿蒙版没有 wails3 壳（wails3 官方不支持鸿蒙），所以用 ArkTS 自建壳：ArkWeb + NAPI 加载 Go 编译出来的 c-shared 库（`libhomecast_go.so`），壳调 `StartServer(dataDir)` 把后端在 App 里拉起来，然后 ArkWeb 访问 `127.0.0.1:28976`。

环境：win11 + DevEco Studio 26.0 + OpenHarmony SDK 26 + Emulator26.0（x86_64，OpenHarmony 7.0.0.107，hdc 目标 `127.0.0.1:5555`）。Go 工具链用 `hmgo`（star4277/ohos-go，go1.26.5），跟项目 go 版本匹配。Android 副本仓库在 `C:\Users\a1\homecast`。

## 过程

### 1. 编译 Go 后端为鸿蒙 c-shared 库

`main_harmony.go`（`//go:build openharmony`）导出 `//export StartServer(dataDir *C.char)`：显式设置 `HOME`/`HC_DATA_DIR`/`XDG_*`/`TMPDIR` 到 App 沙盒 `filesDir`，然后 goroutine 里 `server.ListenAndServe("127.0.0.1:" + server.Port)`，错误用 `log.Printf` 不 `log.Fatal`（不能把整个 HAP 弄死）。

编译（x86_64 模拟器 + arm64 真机各一份）：

```bat
set "GOROOT=C:\Users\a1\hmgo"
set "GOOS=openharmony"
set "GOARCH=amd64"   rem 另一份 arm64
set "CGO_ENABLED=1"
set "CC=C:\PROGRA~1\Huawei\DevEco~1\sdk\default\openharmony\native\llvm\bin\clang.exe --target=x86_64-linux-ohos"
cd /d C:\Users\a1\homecast\go
C:\Users\a1\hmgo\bin\go.exe build -buildmode=c-shared -o C:\Users\a1\libhomecast_go.so ./cmd/server
```

产物 `.so` + `libhomecast_go.h` 复制到壳工程的 `entry/src/main/cpp/libs/{abi}/` 和 `cpp/include/`。

### 2. 壳工程落地

- AppScope/app.json5：bundleName `com.homecast.music`
- module.json5：`ohos.permission.INTERNET`
- network_config.json：cleartext HTTP 允许（127.0.0.1）
- EntryAbility.ets：`onCreate` 里 `import { startServer } from 'libentry.so'`，传 `this.context.filesDir`
- Index.ets：先轮询 HTTP 200（最多 100 次 * 200ms）再设 WebView URL，避免首启白屏

### 3. 构建 + 签名 + 安装 + 启动


签名走 DevEco SDK 自带的 `hap-sign-tool.jar`（sign-profile → sign-app → verify-app 三步，本地调试证书），产出 `signing/homecast-signed.hap`。安装：

```bat

hdc shell aa start -a EntryAbility -b com.homecast.music
hdc shell "hilog | grep HomeCast"
```

### 4. 排查链：为什么后端起不来（重点）

逐条日志往里挖，一条比一条深：

1. **`Go backend start failed: {}`** —— 空对象。发现：异常是 `undefined` 时 `JSON.stringify(err)` 本来就输出 `{}`，可读性为零。改 `String(err)` + `JSON.stringify(err)`。
2. **`TypeError: Cannot read property startServer of undefined`** —— 模块是 `undefined`。原因：Index.d.ts 是**命名导出**（`export const startServer`），ArkTS 用默认导入拿到的整个是 undefined。改成 `import { startServer } from 'libentry.so'`。
3. **`SyntaxError: the requested module 'entry' does not provide an export name 'startServer'`** —— 说明 NAPI 注册压根没发生，`Init` 没跑。在 `napi_init.cpp` 三处加 `OH_LOG_Print`（RegisterEntryModule / Init / define_properties）。
4. 日志 **一条 HomeCast 都没有**（RegisterEntryModule 是在 .so 构造器里，最先打），说明 **`libentry.so` 加载阶段就直接失败了**。`hvigorw clean` 强制重编也不行。
5. **`hdc shell` 把设备侧 `libentry.so` 拉下来 `readelf -d`，根因现形**：

```
DT_NEEDED: C:/Users/a1/homecast/wails3/build/harmony/entry/src/main/cpp/libs/x86_64/libhomecast_go.so
RUNPATH:   C:/Users/a1/homecast/wails3/build/harmony/entry/src/main/cpp/libs/x86_64
```

CMake 把 **Windows 构建机的绝对路径**写进了 ELF 的依赖里。设备上当然不存在这个路径 → Go 库加载不了 → libentry.so 整体加载失败 → NAPI 构造函数没执行 → `startServer` 不存在。

### 5. 修复

`CMakeLists.txt`：

```cmake
set(CMAKE_SKIP_RPATH TRUE)          # 不生成 RUNPATH
add_library(homecast_go SHARED IMPORTED GLOBAL)
set_target_properties(homecast_go PROPERTIES
    IMPORTED_LOCATION ${NATIVERENDER_ROOT_PATH}/libs/${OHOS_ARCH}/libhomecast_go.so
    IMPORTED_NO_SONAME TRUE)        # 不加 SONAME 绝对路径依赖
```

重编重装后 readelf：NEEDED 只剩 `libhomecast_go.so`，RUNPATH 消失。

### 6. 成功日志（在 HAP 里的真实顺序）

```
RegisterEntryModule called
NAPI Init called
NAPI exports initialized: status=0
Go backend start requested: /data/storage/el2/base/haps/entry/files
StartServer dataDir=/data/storage/el2/base/haps/entry/files
Go backend start returned: true
```

然后 ArkWeb 初始化、`backend HTTP ready after N retries`、页面加载完成。**模拟器页面上显示出来了。**

> 备注：就绪前 `backend probe` 的 `code:2300007` / `osErr:"111"`（111=ECONNREFUSED）/ `tcpConnE:"115"` 是轮询期正常失败日志，不能当失败证据。得认 `start returned: true` + 页面事件。

## 为什么迷你 C 加载器能跑，正式 HAP 却挂？

之前用最小 C 加载器在模拟器 `dlopen` + `StartServer` 是成功的。那是**直接把设备上的 .so 当文件加载**，路径给对了就成。而正式 HAP 的问题是把构建机绝对路径写进了 libentry.so 的 ELF 头，走的是动态链接器按依赖找库的路子——两码事。所以「能跑」和「HAP 里挂」不矛盾，之前差点被这个不一致带偏。

## 结论（个人版）

1. **c-shared 交叉编译 + NAPI 壳这个架构是通的**：Go 后端在正式 HAP 沙盒里用 `filesDir` 起 HTTP，ArkWeb 走 `127.0.0.1:28976`，首页真实显示。业务逻辑零改动。
2. **踩坑本质**：imported 库的路径被写死进产物。凡是"构建机路径 vs 运行机路径"的差异，第一反应去 `readelf -d` 看 NEEDED/RUNPATH/SONAME，比猜 NAPI、猜签名快得多。
3. 排查姿势有效：异常先确保可读（`String(err)`），再靠 hilog 把「注册/导出/调用」三段都埋点，快速收缩到「库压根没加载」。
4. 遗留：搜索/播放最小链路还没在模拟器验证（首页显示 ≠ 全部通过）；host 侧 `hdc fport` 后宿主机 curl 28976 还有 connection reset 现象，但那是宿主侧调试问题，App 内显示成功与之无关。
