## 一、影响性能

### 1. 🔴 DLNA 投屏发现全串行，最坏 N×3s 卡界面

**位置**：`go/internal/dlna/discovery.go` L49-72

`Search` 对 3 个 searchTypes **逐个串行** `ssdp.RawSearch`（每个内部 3 次尝试），全跑完才进第二个循环**再逐个串行** `fetchFriendlyName(d.Location)`（每个 3s timeout）。

- 3 类 × 3 次 × timeout 最坏 9×timeout；
- 再 N 台设备 × 3s 串行拉描述。

发现 5 台慢设备时界面卡十几秒。

**修法**：两类循环都改并行（goroutine + `sync.WaitGroup` + 结果合并）；或至少把 `fetchFriendlyName` 循环并行化。

### 2. 🔴 `controller()` 持锁做网络 I/O

**位置**：`go/internal/service/cast/cast.go` L246-268

```go
func (c *CastService) controller(udn string) (*deviceController, error) {
	c.mu.Lock()          // ← 持锁
	defer c.mu.Unlock()
	...
	avs, err := av1.NewAVTransport1ClientsByURL(u)  // ← 拉设备描述 XML，网络请求
```

首次对某设备投屏/控制时，`NewAVTransport1ClientsByURL` 是**网络调用**，却在 `c.mu` 锁内执行。期间 `DeviceList()`/`Status()`/其他设备操作全部阻塞。若设备离线，该调用挂起至超时，**整服务锁死**。

**修法**：网络调用移出锁——先用 `double-check`（锁内只查 map，未命中先解锁去拉，再拿锁写入），或 per-udn `sync.Mutex`。

### 3. 🔴 音频缓存：上游 chunked（无 Content-Length）时永不缓存

**位置**：`go/internal/api/music.go` Stream 回写分支 + `cache.go:StreamAndCache`

```go
// music.go
if h.Cache != nil && h.Cache.LimitMB() > 0 && r.Header.Get("Range") == "" && upResp.StatusCode == http.StatusOK {
	h.Cache.StreamAndCache(w, bvid, quality, upResp.Body, upResp.ContentLength)
}
```

```go
// cache.go StreamAndCache
if contentLength > 0 && n == contentLength {   // ← contentLength<=0 永远 false
	os.Rename(tmp, ...); s.Put(...)
} else {
	os.Remove(tmp)
}
```

`contentLength > 0` 是落盘门槛。B站 CDN 若返回 **chunked（Content-Length=-1）**，则永远走 else 丢弃，**缓存功能对这类流完全失效**（每次播放都回源 + 白写 .tmp）。且 `StreamAndCache` 已把整流 `io.Copy(io.MultiWriter(w,f), body)` 转发给浏览器后才发现不缓存——白写一份 .tmp。

**修法**：加 `knownLen := contentLength > 0` 分支——未知长度但**流完整读到底**（`io.EOF` 正常结束且 `n>0`）也可落盘；或先读入内存判断。

### 4. 🟡 缓存命中每次都写 SQLite（LRU 触碰写库）

**位置**：`cache.go:Get` L129-137 + `music.go:serveFile`

`Stream` 命中缓存 → `Cache.Get` 每次 `INSERT ... ON CONFLICT UPDATE last_used`。拖动进度条浏览器发多个 Range 请求，每次命中都写一次库（`http.ServeFile` 处理 Range 也走这里）。**低效但低频**。

**修法**：last_used 触碰改内存计数，每 N 次或每分钟批量落库；或只对 `GET` 全量请求触碰，Range 跳过。

## 二、低能

### 1. 🔴 代理 token 永不清理、无 TTL（内存泄漏 + 永久有效）

**位置**：`go/internal/service/token/token.go` L28-44

```go
func (t *TokenStore) Store(...) string { ... t.m[token] = ... }  // 只增不删
func (t *TokenStore) Get(token string) (TokenEntry, bool) { ... } // 不删、不校验过期
```

- 每次音箱投送 / DLNA 投屏都 `Store` 一个 token，**永不清理** → 长跑后内存 map 无限增长（内存泄漏）。
- token **无过期时间** → 任何拿到该 URL 的人**永久**能访问本机代理（安全性），且旧 token 永远有效（本应短命）。

**修法**：`TokenEntry` 加 `expires`（如 1h），`Get` 惰性清理过期项；或加容量上限 + 定期清扫 goroutine。

### 2. 🟡 cast 直链判断重复 + `EpisodesList` 死字段

**位置**：`cast.go` `Sniff` L95-107 内联循环 vs `isDirectVideoURL` L141-146（同样的 `videoExts` 循环）——**重复代码**；`SniffResult.EpisodesList`（L34）声明了但**从未填充**（永远 nil），前端若读 `episodes_list` 永远空。

**修法**：`Sniff` 复用 `isDirectVideoURL`；删 `EpisodesList` 或真正填充。

### 3. 🟡 `itoa` / `loadLimit` 两包重复实现

**位置**：`cache.go` L97-104 / L74-90 与 `lyriccache.go` L57-64 / L41-55

`cache.go` 和 `lyriccache.go` 各有一份**几乎一样的** `itoa()` 和数字解析版 `loadLimit()`。DRY 违规，改一处忘另一处就是 bug。

**修法**：抽公共小包（如 `internal/store/conv` 或各自引用）。

### 4. 🟢 bilibili client 的 `io` 占位

**位置**：`client.go` `var _ = io.Discard`（L96）

未使用的 `io` import 用占位变量掩盖——本可直接删 import。低能。

### 5. 🟢 `discovery.go` 的 `targetIP` 死参数

**位置**：`discovery.go` L35 `func Search(ctx, timeout, targetIP string)` + `cast.go:Discover` 传 `""`

`targetIP` 参数**从未在函数体使用**，`cast.go` 还传空串。死参数 + 多播地址硬编码，想指定网卡/单播发现做不到。

**修法**：删参数，或真正用于绑定多播接口。

## 三、前后不一

### 1. 🟡 proxy.go 无 context 取消（与 music.go 行为不一致）

**位置**：`proxy.go` `stream` L31-38 vs `music.go` Stream

`proxy.go` 用裸 `http.NewRequest` + `client.Do(req)`，**没有 `req = req.WithContext(r.Context())`**。客户端断开后，代理仍把上游整个流读完才返回——浪费带宽/连接，且音箱/DLNA 长流场景更明显。`music.go` 的 `GetRaw` 同样不带 context（同源问题）。

**修法**：两处都 `req.WithContext(r.Context())`，客户端断开即取消上游。

### 2. 🟢 `ClearUnfav` 用字符串拼接表名（两处一致，但风格危险）

**位置**：`cache.go:ClearUnfav` L212 + `lyriccache.go:ClearUnfav` L147

```go
`... WHERE bvid NOT IN (SELECT bvid FROM ` + favTable + `)`
```

两处都拼表名。目前 `favTable` 是代码内常量（`fav.FavTable`）故安全，但这是**注入形状**——哪天表名来自外部就中招。且两包各自实现，未收敛。

**修法**：表名白名单校验，或抽公共函数。
